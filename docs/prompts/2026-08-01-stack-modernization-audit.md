## §0. Что требуется на выходе — в одном абзаце

Провести исчерпывающий аудит **всех без исключения** технологических компонентов проекта, для каждого установить актуальную версию по состоянию на 2026-08-01 через веб-исследование первоисточников, оценить разрыв и риск обновления, отдельно выбрать актуальные LLM- и image-модели, и собрать исполняемый план обновления по волнам. ## §1. Миссия и границы

### 1.1. Входит в scope

1. **Инвентаризация 100% стека** — все версии из всех манифестов, Dockerfile, compose-файлов, CI-workflow и конфигов моделей. Полнота проверяемая (§11).
2. **Веб-исследование по каждому компоненту** с актуальностью на 2026-08-01: последняя стабильная версия, дата релиза, breaking changes, CVE, EOL.
3. **Матрица версий** «текущая → целевая» с решением, риском и трудозатратой по каждой позиции.
4. **Отдельный трек выбора AI-моделей** — LLM для извлечения сущностей/описаний и модель генерации изображений, с моделью стоимости.
5. **План обновления по волнам** с порядком, проверками и откатом.
6. **Исполнение обновления** — после стоп-точки §12.1.

### 1.2. Явно НЕ входит в scope

| Не делать | Почему |
| --- | --- |
| Обновление документации под новые версии | Отдельная задача пользователя; здесь только **список** доков, требующих правки, в артефакте `docs/_drafts/2026-08-01-docs-impact-list.md` |
| Рефакторинг функциональности, оптимизация архитектуры | Отдельная задача; здесь только обновление версий и минимально необходимые правки совместимости |
| Деплой на прод, миграции боевой БД | Стоп-точка §12.2 — граница жёсткая |
| Изменение бизнес-логики, UX, схемы данных | Кроме случаев, когда этого требует breaking change обновляемой зависимости — и тогда с явной пометкой |
| Расширение тестового покрытия | Кроме тестов, чинящих поломки от обновления |

**Ловушка scope creep.** По ходу аудита будет очень соблазнительно чинить найденный техдолг. Не чини — **записывай** в `docs/_drafts/2026-08-01-tech-debt-backlog.md`. Исключение: пункты из §5.1, они блокируют сам процесс обновления и входят в Волну 0.

## §3. Принципы работы

### 3.1. Иерархия источников истины

1. **Работающий прод** (`ssh fancai`) — что фактически исполняется прямо сейчас: версии внутри контейнеров, теги образов, коммит деплоя, боевые переменные окружения. Высший приоритет по вопросу «как есть», см. §4.10.
2. **Код и манифесты репозитория** — что **должно** стоять: `backend/requirements.txt`, `frontend/package.json`, оба `package-lock.json`, `backend/Dockerfile.*`, `frontend/Dockerfile.*`, `docker-compose.*.yml`, `.github/workflows/*.yml`, `backend/app/core/config.py`.
3. **Первоисточники вендора** — что доступно сейчас: официальные release notes, CHANGELOG в репозитории проекта, PyPI/npm registry, официальная документация.
4. **Агрегаторы** — `endoflife.date`, GitHub Security Advisories, CVE-базы.
5. **Блоги, статьи, обсуждения** — только как указатель на первоисточник, не как доказательство.

Расхождение п.1 и п.2 — не досадная мелочь, а находка первого класса: перед релизом она означает, что боевая конфигурация частично не версионируется.

### 3.2. Не доверяй этому промпту

Инвентарь в §4 снят с манифестов 2026-08-01 и приведён как **seed, а не как истина**. Перед работой пересними его сам — репозиторий мог измениться. Любое расхождение фиксируй отдельно: это само по себе находка.

Так же не доверяй собственным знаниям о версиях: training data устарела по определению. Каждая версия — из сети, с URL и датой.

### 3.3. Доказательность

Утверждение считается доказанным, если приведён URL первоисточника и дата публикации. Формулировки «вероятно, последняя», «насколько мне известно», «обычно» — недопустимы. Если факт установить не удалось, так и пиши: **«не установлено, проверено N источников, блокер: …»**.

### 4.9. Транзитивное дерево, lock-файлы и системные пакеты

Прямые манифесты — вершина айсберга. «Все компоненты» означает и то, что фактически резолвится в сборку.

**Lock-файлы.** В проекте их два, оба npm: корневой `package-lock.json` и `frontend/package-lock.json` (`lockfileVersion: 3`). **У бэкенда lock-файла нет вообще** — ни `uv.lock`, ни `poetry.lock`, ни скомпилированного `requirements.lock`/`constraints.txt`. В сочетании с `pip install --no-cache-dir --upgrade pip`, незапиненным `hypothesis` и плавающим `modal>=0.73` это значит, что две сборки одного коммита могут дать разные деревья зависимостей. Оцени это как отдельную находку и предложи решение (pip-tools / uv lock / constraints-файл) — но **не внедряй без согласования**, это смена инструментария, а не обновление версии.

Что требуется по lock-файлам — **аудит дерева, а не карточка на каждый транзитивный пакет** (их тысячи, это не масштабируется и не нужно):

1. Прогнать аудит уязвимостей: `npm audit --json` в обоих npm-деревьях, `pip-audit -r backend/requirements.txt` для Python. Разобрать каждую находку High/Critical: достижима ли она в проекте, есть ли фикс, тянет ли мажор.
2. Найти дубли и конфликты версий внутри дерева: `npm ls --all` на предмет нескольких копий одного пакета, особенно тяжёлых. Корневой и фронтовый `package-lock.json` резолвят пересекающиеся наборы по-разному (см. §5.2, п. 6) — установить, какие пакеты разошлись фактически.
3. Проверить актуальность блока `overrides` в `frontend/package.json` (`brace-expansion`, `cross-spawn`, `serialize-javascript`): это следы закрытых CVE. Если апстрим уже поднял версии, override стал мёртвым кодом, который маскирует реальное дерево.
4. **Обязательная регенерация после обновлений:** удалить lock, выполнить чистую установку, зафиксировать новый lock, затем повторно прогнать аудит и сборку. Обновление `package.json` без регенерации lock — обновление на бумаге.
5. Транзитивные карточки заводить только на пакеты, которые всплыли как проблемные: CVE, конфликт версий, заброшенность, лицензия.

**Системные пакеты образов.** Обновляются вместе с базовым образом и почти никогда не пересматриваются:

| Образ | Слой | Пакеты |

| `backend/Dockerfile.prod` | runtime (`apt-get`) | `libpq5`, `curl` |

Ни один `apt-get`/`apk` не пинит версии — это осознанный компромисс, но зафиксируй его как риск воспроизводимости.

### 4.10. Фактическое состояние прода — обязательная сверка

Репозиторий говорит, что **должно** работать. Прод говорит, что работает **на самом деле**. Между ними почти наверняка есть расхождения: ручные хотфиксы, незакоммиченные правки, образы, собранные из другого коммита, изменённые переменные окружения.

**Доступ:** алиас `ssh fancai` (настроен локально в `~/.ssh/config`; реквизиты в репозитории намеренно не дублируются). Инструмент — `ssh://fancai/<path>` для чтения файлов или `ssh` для команд. Если алиас не резолвится — не подбирай хост, останови работу и запроси доступ.

**Строго read-only.** Снимаешь состояние, ничего не меняешь. Никаких `docker compose up/down/pull`, `apt upgrade`, `systemctl restart`, правок файлов, миграций. Любое изменение прода — стоп-точка §12.2.

Минимальный снимок:

| Что установить | Как |
| --- | --- |
| Точное состояние checkout'а | `git -C <путь-деплоя> rev-parse HEAD`, `git branch --show-current`, `git status --porcelain`, `git diff --name-status`, `git diff --cached --name-status`. Короткого `log -1` мало: нужен полный SHA и полный список незакоммиченных и заиндексированных правок |
| Связь «образ ↔ коммит» | `docker compose -f docker-compose.prod.yml ps` даёт имена; дальше по каждому контейнеру `docker inspect <c> --format '{{.Image}} {{.Created}}'` и `docker image inspect <image> --format '{{.Id}} {{.RepoDigests}} {{.Created}} {{json .Config.Labels}}'`. **Именно это связывает запущенный контейнер с коммитом** — через OCI-метки (`org.opencontainers.image.revision`, `…created`, `…version`), если они проставлены. Если меток нет — так и запиши: связь образа с коммитом не доказуема, и это само по себе находка для CI |
| Реальные версии внутри Python-контейнеров | `docker exec <backend> pip list --format=freeze`, `docker exec <backend> python -V`, то же для celery-воркера. Сравнивать **нормализованный subset прямых зависимостей** из `requirements.txt` (имя+версия, регистр и `-`/`_` привести к одному виду), а не весь вывод: `pip list` содержит транзитивы, а `hypothesis` без пина и `modal>=0.73` могут законно резолвиться иначе при пересборке. Несовпадение — **сигнал** «образ собран не из текущего `main`», подлежащий проверке, а не доказательство |
| Происхождение фронтенд-образа | Версии из `package-lock.json` внутри прод-образа **извлечь нечем**: финальный слой `frontend/Dockerfile.prod` — это `alpine:3.21`, куда скопирован только статический `dist`; ни Node, ни `node_modules` там нет, а сам сервис в compose собирающий и завершается после сборки. Происхождение доказывается только digest, OCI-метками и SBOM (`docker sbom` / `syft`, если доступны). Если ни одного из этих следов нет — пиши прямо: происхождение фронтенд-сборки не доказуемо, это находка для CI, а не повод выдумывать проверку |
| Версии сервисов | `docker exec <postgres> psql -V`, расширение pgvector: `SELECT extversion FROM pg_extension WHERE extname='vector'`, `docker exec <redis> redis-server -v`, `caddy version` |
| Фактические AI-настройки | **имена** переменных окружения и значения только не-секретных ключей: `AI_PROVIDER`, `GEMINI_BACKEND`, `GEMINI_*_MODEL`, `GCP_LOCATION`. **Секреты не читать и не выводить** |
| ОС и ядро хоста | `cat /etc/os-release`, `uname -a`, `apt list --upgradable` (без установки) |
| Ресурсы — потолок для обновлений | `free -h`, `df -h`, `docker stats --no-stream` |

Последняя строка таблицы не формальность: сервер ограничен по памяти (в compose Redis зажат в 640 МБ, у Postgres `shm_size: 10g`, celery-образ ~2.5 ГБ). Обновление, требующее заметно больше RAM или места на диске, может быть неприменимо физически — это входит в оценку риска.

**Не запускай `docker compose config`.** Команда интерполирует переменные окружения и выводит секреты в открытом виде — в логи сессии и потенциально в артефакты. Состав сервисов бери из файла в репозитории, фактическое состояние — из `ps` и `inspect`. По той же причине не выводи целиком `docker inspect` без `--format`: в `.Config.Env` лежат секреты.

**Результат сверки** — раздел «Прод против репозитория» в основном отчёте и, если расхождения существенные, отдельный артефакт `docs/_drafts/2026-08-01-prod-vs-repo-drift.md`. Каждое расхождение: что в репозитории, что на проде, когда и почему разошлось (если устанавливается), влияет ли на план обновления.

**Если расхождение обнаружено — не «исправляй» прод и не подгоняй репозиторий молча.** Зафиксируй и вынеси в стоп-точку §12.1: расхождение между продом и `main` перед релизом может означать, что часть боевой конфигурации нигде не записана.

## §6. Методология веб-исследования

### 6.1. Якорь даты

Все выводы — **по состоянию на 2026-08-01**. Практически:

- В поисковых запросах ограничивай период: `after:2026-01-01`, при необходимости `before:2026-08-02`.
- Для каждой найденной версии фиксируй **дату релиза**. Версия, вышедшая после 2026-08-01, в матрицу не попадает — но упоминается отдельной строкой «вышло позже якоря».
- Если пакет не обновлялся больше 12 месяцев — это сигнал заброшенности, отметь отдельно и оцени риск.

### 6.2. Инструменты и их приоритет

| Задача | Инструмент |
| --- | --- |
| Известен URL (GitHub releases, PyPI, npm, docs) | `read` по URL напрямую — **не** `web_search` |
| Файл в GitHub-репозитории (CHANGELOG, migration guide) | `github` op `file_read` |
| Документация библиотеки, API, миграционные гайды | `context7` (`resolve-library-id` → `query-docs`) |
| Неизвестен источник, нужен обзор | `web_search` с датовыми директивами |
| Проверка совместимости внутри дерева зависимостей | локально: `pip index versions`, `npm view <pkg> versions`, `npm outdated`, `pip-audit` |

Локальные проверки обязательны и дёшевы — `npm outdated --json` и `pip list --outdated` дают базовый срез за секунды. Но они показывают только то, что резолвится из текущих ограничений; веб-исследование их не заменяет, а дополняет.

### 6.3. Что выяснить по каждому компоненту

Минимальный набор, без которого карточка не считается заполненной:

1. Последняя стабильная версия на 2026-08-01 + дата релиза + URL.
2. Статус текущей версии: поддерживается / security-only / EOL. Дата EOL, если известна.
3. Breaking changes между текущей и целевой — с перечислением конкретных изменений, а не «есть breaking changes».
4. Известные CVE в текущей версии (severity, CVE-ID).
5. Требования к рантайму у целевой версии (минимальный Python/Node).
6. Совместимость с соседями по стеку (пример: SQLAlchemy ↔ Alembic ↔ asyncpg ↔ pgvector; FastAPI ↔ Pydantic ↔ Starlette; Vite ↔ плагины ↔ Rollup; Celery ↔ Kombu ↔ redis-py).
7. Наличие официального migration guide + URL.

### 6.4. Порядок обхода

Иди слоями снизу вверх, потому что нижние слои ограничивают верхние: рантаймы → БД/брокер → фреймворки → библиотеки → инструменты → CI → модели. Версия Python задаёт потолок для пакетов; версия Node — для Vite; версия PostgreSQL — для pgvector.

## §7. Критерии решения по каждому компоненту

### 7.1. Таксономия решений

| Решение | Когда |
| --- | --- |
| `UPGRADE-NOW` | Патч/минор без breaking changes, либо критический CVE |
| `UPGRADE-STAGED` | Мажор с миграцией; требует отдельной волны и проверок |
| `HOLD` | Обновление заблокировано соседом по стеку, либо выгода не оправдывает риск перед релизом. **Обязательно: причина + условие снятия HOLD** |
| `REPLACE` | Компонент заброшен или больше не подходит; нужна замена |
| `REMOVE` | Компонент не используется фактически |

### 7.2. Классы риска

| Класс | Содержание | Проверка после |
| --- | --- | --- |
| R0 | Патч, без изменений API | Прогон тестов слоя |
| R1 | Минор, обратно совместимый | Тесты слоя + сборка |
| R2 | Мажор с точечной миграцией | Полные тесты + сборка + docker build |
| R3 | Мажор с влиянием на архитектуру (ORM, фреймворк, сборщик, рантайм) | Всё выше + ручной smoke ключевых сценариев |
| R4 | Замена компонента | Отдельный план, вне волн обновления |

### 7.3. Предрелизный фильтр

Проект идёт к релизу. При равных прочих — выбирай стабильность: свежая мажорная версия, вышедшая за 2–3 недели до якоря, рискованнее предыдущей зрелой. Такие случаи помечай `UPGRADE-STAGED` с рекомендацией «после релиза» и обоснованием. Обратное тоже верно: сидеть на EOL-версии ради «стабильности» — не стабильность, а отложенный инцидент.

## §8. Отдельный трек — выбор AI-моделей

Самая ценная часть работы: модели меняются быстрее библиотек, а стоят денег на каждом обработанном тексте.

### 8.1. Что фактически нужно от моделей

Прежде чем сравнивать — **прочитай реальные вызовы**, не полагайся на общие представления о задаче: `backend/app/core/gemini_client.py`, `openrouter_client.py`, `ai_provider.py`, `backend/app/services/description_extraction_service.py`, `entity_synthesis_service.py`, `entity_deduplication_service.py`, `nano_banana_generator.py`, `image_generator.py`, `backend/app/prompts/`.

Три рабочие нагрузки:
1. **Извлечение сущностей** из художественного текста на русском — структурированный вывод по схеме, длинный контекст (чанки до ~100К символов), важна полнота и отсутствие галлюцинаций имён.
2. **Извлечение визуальных описаний** — структурированный вывод, чувствителен к качеству понимания образности.
3. **Генерация изображений** по извлечённому описанию — сейчас с промежуточным переводом RU→EN.

### 8.2. Что исследовать

- **Актуальная линейка Gemini на 2026-08-01.** Пользователь назвал «Gemini 3.6 Flash» как пример желаемого — **это иллюстрация намерения, а не подтверждённый факт**. Установи реальный состав линейки, точные идентификаторы моделей, даты GA и статус текущих `gemini-3.5-flash` / `gemini-3.1-flash-lite` / `gemini-3.1-flash-image` (актуальны / deprecated / sunset date).
- **Доступность в обоих бэкендах** — Developer API и Vertex AI, с учётом того, что проект использует `GCP_LOCATION=global` именно потому, что нужная модель отсутствовала в региональных эндпоинтах. Проверь, сохраняется ли это ограничение.
- **Требуемая версия `google-genai`** для целевых моделей — может тянуть обновление SDK как жёсткую зависимость.
- **Каталог OpenRouter** — актуален ли `flux.2-klein-4b`, что есть лучше по цене/качеству, жив ли вообще сценарий OpenRouter после Stage A.
- **Альтернативы для генерации изображений** — наследники Nano Banana, линейка FLUX, Imagen; критерии: качество на сценах из художественной прозы, цена за изображение, латентность, ограничения по контенту.
- **Возможности, влияющие на стоимость:** context caching, batch API, thinking budget / контроль рассуждений, tiering (лёгкая модель на простых чанках).

### 8.3. Обязательный результат трека

1. **Таблица сравнения** кандидатов: идентификатор, окно контекста, поддержка structured output/JSON-схем, thinking control, context caching, batch, цена вход/выход/кэш за 1M токенов, rate limits, доступность в Developer/Vertex, дата GA.
2. **Модель стоимости**: оценка текущих расходов на обработку одной книги и месячных при текущем профиле нагрузки — и то же для рекомендованного варианта. С формулой и допущениями, а не одним числом.
3. **Рекомендация**: primary LLM, fallback LLM, image-модель — с точным списком ключей `config.py`, которые надо изменить.
4. **Оценка влияния на промпты**: смена модели часто требует правки промптов и схем. Определи, нужна ли, и опиши объём. Если нужна — это отдельная задача, не делай её здесь.
5. **План smoke-проверки** новых моделей на реальном тексте до переключения дефолта.

### 8.4. Не решай в одиночку

Значение `AI_PROVIDER` по умолчанию, переход на Vertex как основной бэкенд и выбор image-модели имеют денежные и качественные последствия. Подготовь рекомендацию с обоснованием и вынеси на согласование в стоп-точке §12.1, а не меняй молча.

- Одна волна — один коммит (или несколько атомарных внутри волны), формат по `CONTRIBUTING.md`: `chore(deps): ...`, `build(docker): ...`, `ci: ...`, `feat(ai): ...`.
- После каждой волны — проверки из её критерия выхода. Волна не считается закрытой, пока проверки не прошли.
- **Обновил `package.json` — регенерируй lock в той же волне.** Чистая установка, новый `package-lock.json` в коммит, повторный `npm audit`. Правка манифеста без регенерации lock — обновление только на бумаге: собираться будет старое дерево.
- Поломка внутри волны: чини в рамках волны, если это правка совместимости. Если поломка вскрывает архитектурную проблему — откатывай пакет в `HOLD` и записывай в backlog, не втягивайся в рефакторинг.
- Веди журнал `docs/progress.md` по ходу — по одной записи на волну.

## §12. Стоп-точки

### 12.1. Обязательная пауза после Фазы 4

Собрав матрицу, трек моделей и план — **остановись и вынеси на согласование**. Массовое обновление зависимостей перед релизом и смена AI-моделей влияют на стоимость и качество продукта; решение за пользователем.

В сводке для согласования: сколько компонентов в каждой категории решений, что несёт наибольший риск, рекомендация по моделям с ценой, что предлагается отложить на после релиза и почему.

### 12.2. Жёсткая граница

Без отдельного явного разрешения не делать: деплой на прод, запуск чего-либо из `scripts/` (все скрипты там трогают продакшен, `migration-restore.sh` разрушителен), траты на платные API сверх дешёвых smoke-проверок.

**Доступ к проду — только на чтение.** Сверка §4.10 разрешена и обязательна: `ps`, `inspect --format`, `image ls`, `pip list`, `-V`/`--version`, чтение имён env-ключей и значений неконфиденциальных, `free`/`df`, `uname`, `os-release`. Запрещено без отдельного разрешения: `up`/`down`/`restart`/`pull`/`build`, изменение файлов, `apt upgrade`, чтение и вывод значений секретов, `docker compose config`.

**Боевая БД — узкая щель, а не глухой запрет и не свобода.** Снимок §4.10 обязателен, поэтому граница проходит по типу запроса, а не по факту подключения.

Разрешено, read-only и только это:

- метаданные сервера и расширений: `psql -V`, `SHOW server_version`, `SELECT extversion FROM pg_extension WHERE extname='vector'`, перечень расширений и параметров конфигурации;
- агрегаты **без выборки содержимого строк**, нужные для модели стоимости §8.3: `COUNT(*)` по книгам/главам/сгенерированным изображениям, `SUM`/`AVG` по токенам и стоимости из таблицы `llm_usage_log`, `pg_database_size`, размеры таблиц. Это цифры о нагрузке, а не пользовательские данные.

Запрещено без отдельного разрешения:

- любые `INSERT`/`UPDATE`/`DELETE`/`TRUNCATE`, DDL, `alembic upgrade`/`downgrade`, `VACUUM FULL`, изменение настроек;
- чтение **содержимого** прикладных строк: тексты книг и глав, извлечённые описания и сущности, промпты, email и любые поля пользователей, токены, содержимое сессий. Агрегат — можно, строку — нельзя;
- любые записи в Redis, включая `FLUSHDB` (напоминание: DB 1 — брокер Celery, её потеря убивает очередь);
- перенос сырых выборок в артефакты: в отчёт идут числа и выводы, а не дампы.

Нужна величина, которую нельзя получить агрегатом — не добывай сам, сформулируй вопрос и вынеси в §12.1.

**Логи прода — не источник для этой задачи.** Не читай `docker logs` и файлы в `logs/` подряд: там тексты книг и извлечённые описания (пользовательский контент), промпты, возможные токены в заголовках и stack traces с окружением. Для инвентаризации стека логи не нужны. Если версия или факт старта иначе не устанавливаются — возьми минимальный ограниченный фрагмент под конкретный вопрос (`--tail` в единицах строк, по возможности с grep по версии), просмотри локально и **перенеси в артефакт только извлечённый факт, никогда не сырые строки**.

При необходимости smoke-теста платной модели — сначала оцени стоимость проверки и назови её.

## §13. Форма отчётности

Промежуточные проверки внутри фазы делай молча. Отчёт — по завершении фазы, коротко: что установлено, что оказалось не так, как ожидалось, что дальше.

В финальной сводке обязательно раздел **«Чего не удалось установить»** с перечнем и причиной по каждому пункту. Пустой раздел при аудите такого объёма подозрителен — скорее всего, что-то не проверялось.
