# Промпт: Исследование VPS/VDS серверов в РФ для проекта fancai

> **Назначение:** Передать Claude Opus 4.6 для проведения масштабного веб-исследования VPS/VDS провайдеров с локациями в России.
> **Модель:** Claude Opus 4.6 с доступом к веб-поиску
> **Ожидаемый результат:** Подробный аналитический отчёт в `/docs/reports/` на русском языке

## Промпт

Проведи масштабное, глубокое исследование рынка VPS/VDS серверов с локациями в Российской Федерации для production-хостинга проекта fancai. Изучи актуальные предложения провайдеров на февраль-март 2026 года, сравни их по всем критически важным для проекта параметрам, и выдай обоснованные рекомендации с учётом реальных потребностей проекта.

### О проекте fancai

fancai — это AI-приложение для чтения художественных книг (EPUB/FB2), развёрнутое в продакшене на fancai.ru. Две ключевые AI-функции: (1) генерация иллюстраций к книгам через Gemini 3.0 Flash + Imagen 4, (2) интерактивная энциклопедия сущностей — персонажи, локации, объекты с спойлер-защитой по главам. Проект в стадии активной разработки, текущий сервер (4 ядра, 8 ГБ RAM) уже на пределе.

### Полный стек технологий и сервисов

### Профиль нагрузки — почему нужен мощный сервер

**AI-пайплайн обработки книг (самая тяжёлая операция):**

- Одна книга = N глав × Gemini-вызовов + 1 LLM-дедупликация + ceil(entities/50) синтез-вызовов
- Каждая глава разбивается на чанки по 100K символов, до 10 глав обрабатываются параллельно (asyncio.Semaphore)
- Celery-задача обработки книги имеет hard limit 3 часа, soft limit 2ч55м
- Книга из 300 глав с 100 сущностями = ~303 вызова Gemini API
- При обработке в памяти одновременно: 10 × 100K-символьных строк + JSON-ответы Gemini + промежуточные структуры Pydantic
- Генерация изображений: перевод RU→EN через Gemini + Imagen 4 API, каждое 1-3 МБ PNG

**PostgreSQL — тяжёлые запросы:**

- Таблица `chapters` хранит полный текст всех глав (500-страничный роман ≈ 300-500 КБ)
- Таблица `generated_images` хранит base64-строки (на 33% больше бинарника) — до 4 МБ на запись
- EntityService.get_book_entity_network() — 6 последовательных запросов по связанным таблицам (entities, descriptions, mentions, relationships, events)
- JSONB-поля: biography_milestones, entity_metadata, aliases_with_reveal — растут с каждой главой
- Пул соединений: pool_size=20, max_overflow=40, → 60 соединений на процесс, при 2 worker'ах = 120 (превышает max_connections=100)

**Redis — 7 конкурирующих нагрузок в 640 МБ:**

1. Celery broker + results (gzip-сжатые)
2. Кэш приложения (entity networks, chapters, metadata)
3. Кэш LLM-ответов (24ч TTL, каждый — крупный JSON)
4. Распределённые блокировки книг (3ч TTL)
5. Blacklist JWT-токенов
6. Rate limiter
7. PubSub для прогресса обработки

**Файловое хранилище:**

- EPUB/FB2 файлы на диске (сейчас ~100 МБ, растёт с каждым пользователем)
- PNG-иллюстрации на диске (1-3 МБ каждая, до 500 на премиум-пользователя)
- Ежедневные бэкапы pg_dump + gzip хранятся 7 дней локально перед загрузкой в S3

### Целевые характеристики сервера

На основе реальных потребностей проекта (текущий стек + Sentry + мониторинг + запас на масштабирование до 100 активных пользователей):

| Параметр   | Минимум    | Оптимум            | Обоснование                                                                                                                                  |
| ---------- | ---------- | ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------- |
| **CPU**    | 8 ядер     | 10-12 ядер         | 6.2 CPU по лимитам Docker + Sentry (2-3 CPU) + мониторинг (1 CPU) + запас                                                                    |
| **RAM**    | 24 ГБ      | 28-32 ГБ           | 7.8 ГБ текущие сервисы + 6 ГБ Sentry + 2 ГБ мониторинг + 4 ГБ масштабирование Celery/PG + 2-4 ГБ ОС/swap                                     |
| **Диск**   | 50 ГБ NVMe | 80-100 ГБ NVMe     | 15 ГБ Docker-образы + 10-20 ГБ PostgreSQL (текст глав + base64 картинок) + 10-20 ГБ файлы (EPUB + PNG) + 10 ГБ бэкапы + 10 ГБ Sentry + запас |
| **Трафик** | 5 ТБ/мес   | Безлимитный        | EPUB-загрузки (до 30 МБ) + PNG-иллюстрации + API-ответы + WebSocket                                                                          |
| **Порт**   | 1 Гбит/с   | 1+ Гбит/с          | Нет CDN, всё раздаётся с сервера                                                                                                             |
| **Бюджет** | —          | 7 000–10 000 ₽/мес | Жёсткий потолок                                                                                                                              |

### Критически важные технические требования

1. **NVMe обязательно** — PostgreSQL с JSONB + AOF-персистенция Redis + Docker overlay FS = высокая нагрузка на дисковый I/O. Обычный SSD приведёт к деградации при параллельной обработке книг.

2. **KVM-виртуализация** — Docker требует полного ядра Linux. OpenVZ/LXC не подходят (ограничения cgroups, отсутствие модулей ядра).

3. **Честные ядра (не shared/oversold)** — AI-обработка книг загружает CPU на 100% во время пиков (10 параллельных Gemini-запросов + Celery concurrency=4 + PostgreSQL queries). Shared-ядра приведут к непредсказуемой деградации.

4. **Своп** — Возможность создать 2-4 ГБ swap (vm.swappiness=10) как страховку от OOM при пиковой обработке.

5. **Root-доступ** — Docker, UFW, crontab, sysctl, custom nginx configs. Без root ничего не работает.

6. **Стабильный uptime** — Приложение в продакшене с реальными пользователями. SLA ≥ 99.9%.

7. **DDoS-защита** — L3/L4 обязательно (желательно включена). L7 — желательно (у нас свой rate limiting в nginx, но базовая защита нужна).

8. **Бэкапы / Снапшоты** — Автоматические снапшоты сервера как дополнительная страховка (основные бэкапы БД делаем сами через pg_dump → S3).

### Сценарий масштабирования до 100 активных пользователей

«Активный пользователь» = читает книги и загружает новые. При 100 активных пользователях:

- **Одновременные API-запросы:** 20-30 (чтение сессий, загрузка глав, получение сущностей)
- **Одновременная обработка книг:** 2-4 книги (heavy-очередь Celery)
- **Генерация иллюстраций:** 10-20 Imagen-задач в normal-очереди
- **PostgreSQL connections:** 60-80 активных (pool_size нужно будет скорректировать)
- **Redis memory:** 640 МБ уже мало — нужно 1-1.5 ГБ для кэшей 100 пользователей
- **Файловое хранилище:** ~5-10 ГБ EPUB + ~10-20 ГБ PNG за первый год

### Что исследовать по каждому провайдеру

Для каждого провайдера найди и задокументируй:

**Тарифы и конфигурации:**

- Все подходящие тарифы в диапазоне 7-10K ₽/мес (можно шире — 5-12K ₽/мес для сравнения)
- Точные характеристики CPU (модель процессора, частота, shared vs dedicated ядра)
- Объём RAM и тип (ECC?)
- Тип и объём диска (NVMe? какой IOPS?)
- Тип виртуализации (KVM/QEMU обязательно)
- **Наличие конфигуратора (кастомная сборка)** — многие провайдеры позволяют самостоятельно подбирать характеристики сервера (CPU, RAM, диск) вместо выбора из фиксированных тарифов. Это критически важно для нашего проекта, потому что стандартные тарифы часто имеют перекос (например, много диска при малом RAM, или много ядер при малом диске). Нам нужна конкретная конфигурация: 8-12 ядер + 24-32 ГБ RAM + 50-100 ГБ NVMe — именно конфигуратор может позволить собрать такой сервер точно под потребности и уложиться в бюджет. Для каждого провайдера с конфигуратором — собери оптимальную конфигурацию под наши требования и укажи её итоговую цену. Для провайдеров без конфигуратора — укажи ближайший подходящий фиксированный тариф и отметь, чего не хватает или что избыточно.

**Сеть и защита:**

- Скорость порта (100 Мбит, 1 Гбит, 10 Гбит?)
- Лимит трафика (безлимит? сколько ТБ?)
- DDoS-защита: что включено бесплатно, что за доплату, мощность (Тбит/с), уровни (L3/L4/L7)
- Наличие приватной сети / VLAN
- IPv4 включён? IPv6?

**Надёжность:**

- SLA (процент uptime)
- Дата-центры: точное расположение, Tier (II/III/IV), сертификации
- Резервирование питания, каналов связи
- Реальные отзывы о стабильности (проверь на habr.com, hostings.info, lowendtalk, Telegram-каналы хостинг-сообществ, отзывы в Google/Yandex)

**Бэкапы и восстановление:**

- Автоматические бэкапы / снапшоты — бесплатно или платно? Какая стоимость?
- Частота снапшотов
- Скорость восстановления из снапшота
- Возможность ручного создания снапшота перед обновлениями

**Биллинг и оплата:**

- Помесячная оплата vs годовая (размер скидки)
- Почасовой биллинг?
- Способы оплаты (МИР, СБП, ЮMoney, криптовалюта, безнал для ИП/юрлиц)
- Тестовый период?
- Возврат средств?

**Масштабируемость:**

- Апгрейд без миграции (vertical scaling)?
- Время применения апгрейда
- Максимальная доступная конфигурация у провайдера

**Поддержка и управление:**

- Время ответа техподдержки, каналы (тикет, чат, телефон)
- API для управления сервером (полезно для автоматизации)
- Панель управления (web console, VNC, IPMI)
- Доступность образов ОС (Ubuntu 22.04/24.04, Debian 12)

### Важные уточнения

- **Мне НЕ нужен облачный хостинг типа Yandex Cloud / VK Cloud** — нужен именно VPS/VDS (виртуальный выделенный сервер), а не pay-per-use облачная инфраструктура с непредсказуемыми счетами.
- **Выделенный сервер (dedicated)** — можно рассмотреть, если цена конкурентна с VPS в рамках бюджета 10K ₽/мес.
- Все цены в рублях, все провайдеры с серверами на территории РФ.
- Если по какому-то провайдеру не удаётся найти точные цены — укажи это явно, не придумывай.
