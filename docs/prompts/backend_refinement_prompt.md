# Промпт для Анализа и Доработки Бэкенда (Entity Cards System)

Этот промпт предназначен для Gemini 3 Pro (High). Его цель — подготовить backend-архитектуру к внедрению богатого функционала Карточек Сущностей на фронтенде.

---
**Роль:** Senior Backend Python Developer (FastAPI + SQLAlchemy + PostgreSQL).

**Контекст:**
Мы разрабатываем систему "Entity Cards" для читалки книг. У нас уже есть утвержденный дизайн UI/UX (см. `ui-ux-entity-cards-concept.md`), который требует:
1.  **Spoiler Protection:** Фронтенд должен знать, в какой главе произошло событие или описание, чтобы скрыть его, если пользователь еще не дочитал.
2.  **Rich Visuals:** Портреты, биографии, связи (Relationships).
3.  **Deduplication:** В базе данных много дубликатов сущностей (проблема этапа Extractor).

**Твоя Задача:**
Проанализируй текущий код бэкенда и подготовь детальный план рефакторинга (Implementation Plan) и спецификацию API.

**Входные файлы для анализа:**
*   `backend/app/models/entity.py` (Модель Entity)
*   `backend/app/models/entity_relationship.py` (Связи)
*   `backend/app/models/description.py` (Описания)
*   `backend/app/routers/books/crud.py` (Текущие эндпоинты)

**Требования к решению:**

### 1. API Design (Новый Router)
Спроектируй новый роутер `routers/books/entities.py`.
*   Нам нужен эндпоинт `GET /books/{book_id}/entities/network` (или похожий), который вернет **весь граф** для быстрой работы (In-Reader View должен работать мгновенно).
*   **Response Schema**: Продумай JSON-структуру.
    *   Как передать `chapter_index` для каждого описания (Description)?
    *   Как передать связи (Relationships) так, чтобы фронтенд мог построить граф?
    *   Как пометить "Главных героев" (сортировка по importance)?

### 2. Решение проблемы Дубликатов (Merge Strategy)
Предложи стратегию "на лету" или "в фоне".
*   Если в базе 3 "Геральта", должен ли API отдавать всех 3-х? Или бэкенд должен их сгруппировать по имени перед отправкой?
*   *Рекомендация:* Предложи алгоритм группировки на стороне Python (в Pydantic map), чтобы фронтенд получал уже чистый список уникальных имен.

### 3. Spoiler System Support
*   Убедись, что модель `Description` и `EntityRelationship` пробрасывает поле `chapter_id` или `position` в API-ответ.
*   Если этого поля сейчас нет в схемах Pydantic (schemas), напиши код для их добавления.

### 4. Оптимизация (Performance)
*   Книга может иметь 100+ персонажей и 500+ связей.
*   Нужен ли нам отдельный "Lite" эндпоинт для списка имен (для подсветки в тексте) и "Full" для открытия карточки?

**Результат (Output):**
1.  **Swagger/OpenAPI Spec** (в виде Pydantic моделей) для новых эндпоинтов.
2.  **Python Code Draft**: Пример реализации эндпоинта `get_book_entities` с логикой группировки дубликатов.
3.  **SQLAlchemy Optimizations**: Какие `joinedload` нужно добавить, чтобы не получить N+1 проблему при вытаскивании связей и описаний?
