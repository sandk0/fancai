## Промпт

Ты — старший инженер-исследователь, специализирующийся на методологиях разработки с использованием LLM-агентов. Проведи глубокое, всестороннее исследование экосистемы **Spec-Driven Development (SDD)** инструментов и методологий для LLM-агентов по состоянию на **5 апреля 2026 года**.

### Контекст проекта (для релевантного сравнения)

Исследование проводится для реального production-проекта **fancai** — читалка художественной литературы с AI-иллюстрациями и интерактивной энциклопедией персонажей (spoiler-free). Результаты сравнения должны учитывать специфику этого проекта.

**Технический стек:**

- **Frontend:** React 19 + TypeScript 5.7 + Vite 7 + TanStack Query + Zustand + epub.js 0.3.93 + Tailwind 4 + Radix UI
- **Backend:** FastAPI 0.135.1 + Python 3.12 + PostgreSQL 17 + Redis 7.4 + Celery 5.6 + SQLAlchemy 2.0 + Alembic
- **AI Pipeline:** OpenRouter (Gemini 3.0 Flash — LLM, FLUX.2 Klein — изображения), fallback-цепочки моделей
- **Инфраструктура:** Docker Compose, Caddy 2.11, VPS деплой, мониторинг (Hawk, Netdata, VictoriaMetrics, Uptime Kuma)
- **Размер:** ~130K LOC frontend, ~37K LOC backend, 18 моделей БД, 47 миграций Alembic

**Текущая методология (GSD v1.32.0):**

- Milestone → Phase → Plan → Task — иерархическая декомпозиция
- 26 специализированных агентов (orchestrator, epub-reader, ai-pipeline, entity-system + 22 GSD-инфраструктурных)
- 60 workflow-файлов, 35+ шаблонов планов
- Хуки: pre/post tool use (безопасность, форматирование, контекст-мониторинг), session start, subagent start
- Параллельная работа агентов через git worktrees
- Nyquist-валидация, plan-checker, verifier, integration-checker
- Атомарные коммиты привязаны к планам
- Полная русскоязычная документация планирования

**Масштаб использования:**

- 5 shipped milestones за 1 месяц (v1.0–v1.3 + v1.5 в процессе)
- ~80 фаз, ~90 планов суммарно
- 1 abandoned milestone (v1.4) — стратегический пивот (self-hosted LLM → Modal batch → OpenRouter)
- Соло-разработчик + LLM-агенты

**Ключевые паттерны разработки:**

- Spoiler-free entity система (информация привязана к главам, fuzzy matching ~0.70-0.75 для русских имён)
- CFI-навигация в epub.js (не страницы) — критическое ограничение
- 8 стратегий подсветки описаний (description highlighting) с fallback-цепочкой
- IndexedDB offline кэширование через Dexie
- Tenacity retries + circuit breaker для всех внешних вызовов
- Chunk extraction: 100K chars + 15% overlap для AI-обработки книг

### Измерения для сравнения

Для каждого инструмента оцени по следующим измерениям (оценка 1-10 + обоснование):

#### A. Архитектура и методология

1. **Структурированность планирования** — есть ли иерархия (milestone → phase → plan → task)? Как декомпозируется работа?
2. **Spec-first подход** — требует ли инструмент спецификацию до кода? Как это реализовано?
3. **Трассируемость требований** — можно ли отследить требование → план → коммит? Как?
4. **Верификация и валидация** — есть ли автоматическая проверка выполнения? Какого уровня?
5. **Обработка отклонений** — что происходит, когда план не работает? Есть ли recovery?

#### B. Агентная архитектура

6. **Специализация агентов** — один универсальный агент или много специализированных?
7. **Параллелизм** — могут ли агенты работать параллельно? Как решается конфликт?
8. **Изоляция** — worktrees, sandboxes, или другие механизмы?
9. **Контекст-менеджмент** — как управляется контекстное окно? Compaction? Memory?
10. **Оркестрация** — как координируются множественные агенты?

#### C. Интеграция и экосистема

11. **Поддержка рантаймов** — Claude Code, Cursor, VS Code, терминал, другие IDE?
12. **Расширяемость** — можно ли добавлять свои агенты, workflow, хуки?
13. **MCP/плагины** — интеграция с Model Context Protocol и внешними инструментами?
14. **VCS-интеграция** — атомарные коммиты, PR workflow, branch management?
15. **CI/CD совместимость** — можно ли интегрировать в пайплайны?

#### D. Зрелость и production-readiness

16. **Документация** — полнота, качество, примеры
17. **Сообщество** — размер, активность, звёзды GitHub, contributors
18. **Стабильность API** — частота breaking changes, семантическое версионирование
19. **Скорость релизов** — как часто выходят обновления? Changelog?
20. **Production use cases** — реальные проекты, отзывы, кейсы

#### E. Применимость к проекту fancai

21. **Совместимость со стеком** — Python + TypeScript, монорепо, Docker?
22. **Масштаб проекта** — подходит для ~170K LOC? Или только для маленьких проектов?
23. **Соло-разработчик** — оптимизирован для одного человека + AI или для команд?
24. **Миграция** — сложность перехода с GSD 1.32.0? Что теряется, что приобретается?
25. **Русскоязычная поддержка** — локализация, Unicode, мультиязычные спецификации?

#### F. Методологии за пределами SDD

Исследуй, существуют ли методологии, которые **превосходят** классический SDD подход:

- **Test-Driven Agent Development (TDAD)** — TDD для агентов

- **Formal Methods + LLM** — верификация через формальные доказательства

- **Любые другие подходы**, которые ты найдёшь

### Требования к качеству исследования

1. **Верифицируемость** — каждое утверждение должно быть подтверждено ссылкой (URL, номер версии, дата)
2. **Актуальность** — только данные на апрель 2026. Не используй устаревшую информацию из своих знаний, если есть свежие данные из веба
3. **Глубина** — не поверхностные описания, а реальный анализ. Для каждого инструмента изучи README, changelog, issues, discussions
4. **Объективность** — не продвигай один инструмент. Указывай и сильные, и слабые стороны каждого
5. **Практичность** — каждый вывод должен быть actionable для соло-разработчика проекта на 170K LOC
6. **Полнота** — если в процессе исследования находишь инструменты не из начального списка, включи их
7. **Структурированность** — используй заголовки, таблицы, списки. Документ должен быть удобен для навигации
