## Критические ошибки (требуют исправления)

### 1. ЛОЖНОЕ УТВЕРЖДЕНИЕ: "Rate limiting отсутствует"

**Где**: Отчёт 1, строка 49, раздел P7 (строки 399-402)

**Утверждение**: "Нет FastAPI middleware для rate limiting per-IP/per-user на уровне HTTP"

**Факт**: В проекте **есть** полноценный Redis-based rate limiter:

- `backend/app/middleware/rate_limit.py` — sliding window с декоратором `@rate_limit`
- Пресеты `RATE_LIMIT_PRESETS` включают `ai_image` (5/мин), `ai_entity_extraction` (10/мин), `ai_operation` (10/мин), `normal` (30/мин), `registration` (2/мин)
- Декоратор применён на большинстве AI-эндпоинтов

**Действие**: Исправить таблицу "текущее состояние" и раздел P7. Корректная формулировка: "Rate limiting есть для большинства эндпоинтов, но отсутствует на `process-descriptions` и `reprocess-descriptions` в `crud.py`"

---

### 2. НЕВЕРНАЯ ЦЕНА Claude Haiku 4.5

**Где**: Отчёт 1, строки 147-149

**Утверждение**: Input $0.80 / Output $4.00

**Факт**: Input **$1.00** / Output **$5.00** (на OpenRouter)

**Влияние**: Занижение стоимости fallback на 25%. Все калькуляции с fallback-сценариями дают заниженные цифры.

**Действие**: Исправить таблицу. Пересчитать стоимость при fallback.

---

### 3. КОНФЛИКТ ТАРИФНЫХ ПЛАНОВ между отчётами 2 и 4

**Отчёт 2** (подписочная модель):

- 4 тарифа: Free / Читатель (199₽) / Книгочей (499₽) / Библиотека (999₽)
- Кредиты: 50 (одноразово) / 300 / 800 / 2000
- Анализ главы = **5 кредитов**, изображение = **2 кредита**

**Отчёт 4** (YooKassa):

- 3 тарифа: Free / Basic (299₽) / Pro (490₽)
- Кредиты: 10 / 100 / 500
- Анализ главы = **2 кредита**, изображение = **5 кредитов**

**Проблема**: Стоимости операций в кредитах **перепутаны местами**. Количество тарифов, цены и объёмы кредитов полностью несовместимы.

**Действие**: Принять единую структуру (рекомендуется из отчёта 2 — более проработана) и обновить отчёт 4.

---

### 4. БАГ в SQL-схеме Cost Tracking

**Где**: Отчёт 3, модель `UserAiUsageDaily`

**Проблема**: `__table_args__` содержит `{"schema": None}` вместо `UniqueConstraint("user_id", "date")`. Без этого UPSERT-логика в `flush_ai_costs_to_db` будет создавать дубликаты.

**Действие**: Заменить на:

```python
__table_args__ = (
    UniqueConstraint("user_id", "date", name="uq_user_ai_usage_daily"),
)
```

---

### 5. SQLAlchemy 1.x стиль в примерах кода

**Где**: Отчёт 4 (YooKassa), все модели

**Проблема**: Примеры используют `Column(Integer, primary_key=True)`, `relationship("User", back_populates=...)`. Кодовая база fancai использует SQLAlchemy 2.0: `Mapped[int]`, `mapped_column()`, `lazy="raise"`.

**Действие**: Переписать все модели в стиле SA 2.0. Добавить `lazy="raise"` ко всем relationships.

## Важные ошибки (влияют на точность)

### 6. Расхождение в "средней книге"

| Отчёт            | Средняя книга | Стоимость  |
| ---------------- | ------------- | ---------- |
| 1 (Rate Limits)  | 20 глав       | $0.40-1.60 |
| 2 (Billing)      | 35 глав       | ~$1.99     |
| 5 (Load Testing) | 50 глав       | $0.10-0.20 |

Разница до 8x в количестве глав и непоследовательная стоимость.

**Действие**: Определить единый baseline (рекомендуется: 25 глав — медиана для художественной литературы). Создать файл `docs/research/SHARED_ASSUMPTIONS.md` с согласованными параметрами.

---

### 7. Нереалистичный сценарий Load Testing

**Где**: Отчёт 5, сценарий 6 — "50 пользователей читают одну книгу"

**Проблема**: В текущей архитектуре `Book.user_id` — книги принадлежат одному пользователю. Нет shared books.

**Действие**: Переформулировать: "50 пользователей загрузили идентичную книгу" (тогда LLM cache по content hash сработает).

---

### 8. RPD лимиты бесплатных моделей

**Где**: Отчёт 1, раздел 2.1

**Проблема**: Смешаны лимиты для бесплатных аккаунтов (50 RPD на платные модели) и бесплатных моделей (`:free` суффикс — 200 RPD).

**Действие**: Разделить в таблице. 50 RPD — для неоплативших аккаунтов на ВСЕ запросы, 200 RPD — для моделей с `:free` суффиксом.

---

### 9. Не описана Celery → user_id пропагация

**Где**: Отчёт 3 (Cost Tracking)

**Проблема**: `book_tasks.py:process_book_task()` получает только `book_id_str`. `user_id` нет ни в аргументах задачи, ни в контексте. Все LLM-вызовы пишут `service=None`.

**Действие**: Описать получение `user_id` через `Book.user_id` в DB внутри Celery worker. Или добавить `user_id` как аргумент задачи при enqueue.

---

### 10. Не учтена существующая конфигурация YooKassa

**Где**: Отчёт 4

**Проблема**: `backend/app/core/config.py` уже содержит `YOOKASSA_SHOP_ID`, `YOOKASSA_SECRET_KEY`, `CLOUDPAYMENTS_PUBLIC_ID`. Базовая подготовка уже есть, но отчёт описывает интеграцию с нуля.

**Действие**: Отметить существующую конфигурацию и строить план от текущего состояния.

---

### 11. Security severity завышена

**Где**: Отчёт 6, VULN-AUTH-01 — "Критическая"

**Проблема**: `/validate-file`, `/parse-preview`, `/parser-status` без аутентификации — это DoS-вектор (CPU на парсинг), но нет утечки данных и нет AI-вызовов (нет финансового ущерба).

**Действие**: Понизить до "Высокая". Критическая severity — только для уязвимостей с непосредственным ущербом (data breach, unauthorized access).

## Пробелы, не покрытые ни одним отчётом

| Тема                                     | Почему важно                                                                                    |
| ---------------------------------------- | ----------------------------------------------------------------------------------------------- |
| **WebSocket security** (`/ws` endpoint)  | Аутентификация, rate limiting, abuse — не проверено                                             |
| **CORS misconfigurations**               | Cookie security (SameSite, HttpOnly, Secure) — не аудирован                                     |
| **OpenRouter BYOK transition risk**      | OpenRouter анонсировал возможный переход BYOK на подписку — влияет на стратегию масштабирования |
| **FB2 zip bomb**                         | EPUB проверен на zip bombs, но FB2 (также поддерживается) — нет                                 |
| **`_log_usage_to_db()` fire-and-forget** | `asyncio.create_task()` без await — логи теряются при shutdown                                  |
| **Backfill стратегия**                   | Как мигрировать существующие `llm_usage_log` записи без `user_id`                               |
| **Конкурентный доступ к wallet**         | `SELECT FOR UPDATE` показан, но deadlock-анализ отсутствует                                     |
| **Локализация ошибок платежей**          | Что показывать пользователю при decline разных типов                                            |

## Заключение

Исследования покрывают **~85% необходимой площади** для коммерциализации. Качество отдельных отчётов — от хорошего до отличного (7-9/10). **Главная системная проблема** — отчёты писались параллельно без синхронизации, что привело к конфликтам в тарифных планах, стоимостях операций и описании текущего состояния кода.

Security audit (9/10) — наиболее точный и практически применимый. 2 критические и 5 высоких уязвимостей подтверждены сверкой с кодом. Рекомендуется устранить VULN-AUTH-01 и VULN-COST-01 до начала коммерциализации.

После исправления выявленных ошибок и создания `SHARED_ASSUMPTIONS.md` эти отчёты составят полноценную базу для roadmap коммерциализации.
