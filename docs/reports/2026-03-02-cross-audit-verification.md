## 5. Технические ошибки в server-setup-plan.md

### Фаза 1: Безопасность

| #    | Проблема                                              | Строка/Секция | Рекомендация                                                                                                                                                                                                             |
| ---- | ----------------------------------------------------- | ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| F1.1 | `KexAlgorithms mlkem768x25519-sha256` — совместимость | §1.3          | **Корректно.** OpenSSH 10.0p1 (Debian 13) поддерживает ML-KEM нативно (добавлен в OpenSSH 9.9). PQ-гибридные алгоритмы работают                                                                                          |
| F1.2 | `AllowUsers deploy` + Docker — как работает?          | §1.3          | **Корректно.** Строка 149: `useradd -m -s /bin/bash -G sudo,docker deploy` — user deploy в группе docker, может запускать `docker compose`                                                                               |
| F1.3 | `LogLevel VERBOSE` на production                      | §1.3          | **Приемлемо, но необязательно.** VERBOSE логирует каждый успешный ключ. При 8+ сканерах/час генерирует шум, но fail2ban блокирует быстро. Рекомендация: использовать VERBOSE на первую неделю, затем переключить на INFO |
| F1.4 | `forward chain: policy accept` при Docker             | §1.4          | **Корректно.** Docker управляет своими правилами в FORWARD chain. User-defined policy accept не мешает Docker, т.к. Docker добавляет свои правила с приоритетом                                                          |
| F1.5 | IPv6 SSH ratelimit: `ip6 saddr != ::1`                | §1.4          | **Синтаксис корректен.** В nftables `ip6 saddr` работает в `inet` таблице для IPv6-пакетов. `!= ::1` исключает localhost из rate limiting                                                                                |
| F1.6 | `flush table inet filter 2>/dev/null \|\| true`       | §1.4          | **Безопасно.** Удаляет только таблицу `inet filter`, не затрагивает Docker-таблицы (nat, forward). ### Фаза 3: Ядро

| #    | Проблема                                         | Строка/Секция | Рекомендация                                                                                                                                                                                                           |
| ---- | ------------------------------------------------ | ------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| F3.1 | `vm.overcommit_memory=1` — безопасность          | §3.1          | **Приемлемо с оговорками.** Redis ТРЕБУЕТ `=1` для background save (fork). PG с huge_pages=try совместим. При OOM: oom_score_adj=-900 защищает PG, swap 4GB даёт буфер. Мониторинг memory pressure обязателен          |
| F3.2 | `vm.nr_hugepages=2200` — достаточно ли?          | §3.1          | **Корректно.** 4096MB / 2MB = 2048 страниц + ~150 overhead (lock tables, SLRU buffers) = 2198. Округление до 2200 = +0.1% запас. Можно увеличить до 2300 для безопасности, но 2200 достаточно                          |
| F3.3 | `kernel.panic_on_oops=1` — агрессивно?           | §3.1          | **Обоснованно для БД-сервера.** Oops означает повреждённое состояние ядра. Для сервера с PostgreSQL: продолжение работы с corrupted kernel state опаснее, чем перезагрузка. `kernel.panic=10` даёт 10 секунд до reboot |
| F3.4 | `fs.inotify.max_user_watches=524288` — нужно ли? | §3.1          | **Нужно.** Netdata, Docker, Dozzle — все используют inotify. 524288 — стандартная рекомендация от Docker и Netdata. На dev 65536 (дефолт) может хватить, на prod с 10+ контейнерами и мониторингом — нужен запас       |

### Фаза 6: PostgreSQL

| #    | Проблема                                      | Строка/Секция | Рекомендация                                                                                                                                                                                                               |
| ---- | --------------------------------------------- | ------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
