#### Детали исправлений

**P0-2 — Ошибка истинности Python** (`consistency_manager.py:94`)
- **Что:** `if chapter_index` вычислялось как `False` при `chapter_index=0`, что означало отсутствие маркера главы у visual_summary первой главы, и текст трактовался как «базовый» (всегда показывается), полностью обходя спойлерную защиту.
- **Почему `is not None`:** Единственное безопасное условие присутствия. `0`, пустая строка, `False` — всё это валидные значения, которые должны проверяться явно. Это Python best practice для необязательных числовых параметров.
- **Взаимодействие с P1-1:** После исправления `enumerate(start=1)` первая глава получит `chapter_index=1`, и эта ошибка перестанет срабатывать для новых данных. Но исправление P0-2 остаётся необходимым: оно защищает от регрессий и корректно обрабатывает существующие данные с `chapter_index=0` в БД.

**P1-1 — enumerate off-by-one** (`book_tasks.py:575`)
- **Что:** `enumerate(chapters)` давало `idx=0,1,2,...` тогда как `Chapter.chapter_number` в БД хранится как `1,2,3,...`. Этот `idx` передавался как `chapter_index` в ConsistencyManager (строка 411) и как `chapter_number` в EntityEvent (строка 424).
- **Почему единственная строка исправляет 4 точки:** `idx` используется в двух местах внутри `process_chapter_safe`. Оба автоматически исправляются: строка 411 (`chapter_index=idx`) и строка 424 (`chapter_number=idx`) теперь получают корректное 1-индексированное значение.
- **Чистота Fix:** Не требует миграции схемы. Требует миграции данных для ранее обработанных книг (запланировано отдельно).

**P0-1 — ON CONFLICT не обновляет first_mention_chapter** (`consistency_manager.py:393-414`)
- **Что:** При параллельной обработке глав через `asyncio.gather` INSERT побеждает случайный поток, а не тот, что обрабатывает первую главу. Последующие ON CONFLICT полностью игнорировали `first_mention_chapter`, что оставляло его зафиксированным на значении случайной главы.
- **Почему `LEAST(COALESCE(a,b), COALESCE(b,a))`:** PostgreSQL's `LEAST(NULL, x)` возвращает `NULL`, что нежелательно. Паттерн `LEAST(COALESCE(a,b), COALESCE(b,a))` возвращает минимум двух значений при любой комбинации NULL: если a=NULL → результат b; если b=NULL → результат a; если оба непустые → меньший из них.
- **visual_summary через COALESCE:** Первичное описание первой встречи наиболее информативно. `COALESCE(existing, new)` сохраняет уже записанное значение и заполняет только пустое поле. Полное слияние visual_summary (P2-1) запланировано на следующий спринт.

**P1-2 — Отсутствие инвалидации Redis-кеша** (`book_tasks.py:830-843`)
- **Что:** После завершения полного конвейера обработки книги инвалидировался только `user:{user_id}:books:*`, но не `book:{book_id}:entity_network_raw_v5`. Пользователи, открывавшие глоссарий до повторной обработки, продолжали видеть устаревшие данные до истечения TTL Redis.
- **Почему в существующем try/except блоке:** Логически это продолжение той же операции инвалидации кеша. Уже охватывается обработкой ошибок и логированием. Добавление отдельного try/except избыточно для некритичной операции.

## Резюме для руководства

Архитектура системы Entity Wiki в целом грамотная — паттерн «Кешировать RAW-данные, фильтровать по запросу» в `entity_service.py` хорошо спроектирован, а фронтенд корректно использует 1-индексированные номера глав из mentions. Однако **4 из 7 точек спойлерной фильтрации содержат ошибку "off-by-one"**, вызванную единственной строкой в `book_tasks.py:575`, где используется 0-индексированный `enumerate(chapters)`, тогда как вся остальная система ожидает 1-индексированные номера глав. Кроме того, конструкция `ON CONFLICT DO UPDATE` в `consistency_manager.py` **никогда не обновляет `first_mention_chapter`** — это вероятная первопричина симптома «сущности залипают на последней главе». Ошибка истинности в Python молча отбрасывает визуальные описания для главы 0. Совокупность этих проблем создаёт систему антиспойлеров, которая кажется работающей, но раскрывает информацию на одну главу раньше и некорректно отслеживает первое появление сущностей.


### 1.5 Запрос фронтенда и отображение (1-индексирование)

```
useChapterManagement.ts:36   useState<number>(1)                → начинается с 1

                          ↓

                          ↓

entityUtils.ts:33-36         isNoteSpoiler(): note.chapter_index из Chapter → 1-индексировано ✅
```

### 1.6 Ключевой вывод

Массив **mentions** в `EntityDetailSchema` поступает из JOIN на `Chapter.chapter_number` (1-индексированный), поэтому `isEntityMet()` и `isNoteSpoiler()` работают корректно. Но **события, вехи, псевдонимы, visual_summary** — все проходят через путь с 0-индексированным `enumerate(chapters)`, что делает их смещёнными на единицу при сравнении с 1-индексированной `current_chapter` от фронтенда.

**Итоговый эффект:** События/псевдонимы/вехи из главы N (0-индексирование) фильтруются против `current_chapter=N` (1-индексирование), поэтому они появляются на одну главу РАНЬШЕ. Это утечка спойлеров, а не блокировка.

## 3. Находки по приоритетам

### P0 — Критично (Повреждение данных / Молчаливая потеря данных)

#### P0-1: ON CONFLICT никогда не обновляет `first_mention_chapter`

**Файл:** `consistency_manager.py:393-400`

```python
stmt = stmt.on_conflict_do_update(
    index_elements=["book_id", "name_lower"],
    set_={
        "entity_metadata": stmt.excluded.entity_metadata,
        "aliases_with_reveal": stmt.excluded.aliases_with_reveal,
        "updated_at": func.now(),
    },
)
```

Когда одна и та же сущность встречается в более поздней главе (что типично при параллельной обработке), конструкция ON CONFLICT **обновляет только `entity_metadata` и `aliases_with_reveal`**. При этом НЕ обновляются:
- `first_mention_chapter` — остаётся значением, установленным тем параллельным заданием, которое выиграло гонку
- `visual_summary` — полностью теряется для проигравшей главы
- `importance` — зафиксировано на значении первой обработки

Поскольку `asyncio.gather` обрабатывает все главы параллельно, INSERT выигрывает та глава, которая завершается первой (не обязательно глава 1). Все последующие главы попадают в ON CONFLICT, и их значения `first_mention_chapter` молча отбрасываются. **Это вероятная первопричина симптома «сущности залипают на последней главе», зафиксированного в предыдущем аудите.**

**Исправление:** Добавить `first_mention_chapter` в `set_` с выражением `LEAST(Entity.first_mention_chapter, excluded.first_mention_chapter)`, а `visual_summary` объединять (не заменять).

#### P0-2: Ошибка истинности Python отбрасывает visual_summary главы 0

**Файл:** `consistency_manager.py:94`

```python
chapter_marker = f"[Глава {chapter_index}]" if chapter_index else ""
```

Когда `chapter_index=0` (что происходит из-за ошибки enumerate), `if chapter_index` вычисляется как `False`, и visual_summary первой главы не получает маркер. Это приводит к тому, что:
1. Visual_summary первой главы добавляется без маркера
2. `_process_visual_summary()` трактует текст без маркера как «базовый текст» (показывается всегда), полностью обходя спойлерную защиту

**Исправление:** Заменить `if chapter_index` на `if chapter_index is not None`.

### P1 — Высокий приоритет (Утечка спойлеров)

#### P1-1: Ошибка off-by-one в индексе глав (первопричина)

**Файл:** `book_tasks.py:575`

```python
results = await asyncio.gather(
    *(process_chapter_safe(idx, chapter.id) for idx, chapter in enumerate(chapters)),
    ...
)
```

`enumerate(chapters)` даёт `idx=0,1,2,...`, тогда как `Chapter.chapter_number` в БД равно `1,2,3,...`. Этот 0-индексированный `idx` передаётся в:
- `book_tasks.py:411` → `chapter_index=idx` → ConsistencyManager
- `book_tasks.py:424` → `chapter_number=idx` → EntityEvent
- `consistency_manager.py:94` → маркеры `[Глава N]` в visual_summary
- `consistency_manager.py:384` → `first_mention_chapter=idx`
- `consistency_manager.py:385` → `aliases_with_reveal[].reveal_chapter=idx`

**Исправление:** Использовать `enumerate(chapters, start=1)` или брать `chapter.chapter_number` из объекта БД.

#### P1-2: Redis-кеш entity network не инвалидируется после обработки книги

**Файл:** `book_tasks.py` (секция инвалидации кеша, ~строка 850+)

После завершения полного конвейера извлечения сущностей `book_tasks.py` инвалидирует паттерны кеша `user:*:books:*`, но НЕ инвалидирует `book:{book_id}:entity_network_raw_v5`. Это означает:
- Если кеш был заполнен до повторной обработки, устаревшие данные сущностей сохраняются
- Пользователи видят старые данные до истечения TTL Redis или ручной инвалидации

**Исправление:** Добавить `await redis.delete(f"book:{book_id}:entity_network_raw_v5")` после завершения конвейера.

### P2 — Средний приоритет (Качество данных / UX)

#### P2-1: ON CONFLICT заменяет вместо слияния JSONB-полей

**Файл:** `consistency_manager.py:396-397`

```python
set_={
    "entity_metadata": stmt.excluded.entity_metadata,
    "aliases_with_reveal": stmt.excluded.aliases_with_reveal,
}
```

Когда параллельные обработчики глав создают одну и ту же сущность, ON CONFLICT **полностью заменяет** `entity_metadata` и `aliases_with_reveal` вместо объединения. Если глава 3 добавляет псевдоним «Гарри», а глава 5 — «Мальчик-который-выжил», та, которая завершится последней, перезапишет псевдонимы другой.

**Исправление:** Использовать оператор PostgreSQL `jsonb_concat` или `||` для объединения массивов:
```sql
aliases_with_reveal = entities.aliases_with_reveal || excluded.aliases_with_reveal
```

### P3 — Низкий приоритет (Производительность / Качество кода)

#### P3-1: Ключ TanStack Query включает `currentChapter`

**Файл:** `useEntityNetwork.ts:8-11`

```typescript
export const entityNetworkQueryKey = (bookId: string, currentChapter?: number) =>
    currentChapter != null
        ? ['book', bookId, 'entities', currentChapter]
        : ['book', bookId, 'entities'];
```

Поскольку бэкенд выполняет фильтрацию по главам, каждое изменение главы создаёт новую запись кеша. Для книги из 50 глав это означает 50 отдельных закешированных ответов сети. Учитывая паттерн «кешировать RAW, фильтровать по запросу» на бэкенде, это сделано намеренно (каждая глава возвращает разные данные), но приводит к:
- 50 сетевым запросам на всё прочтение
- Отсутствию повторного использования клиентского кеша между главами

**Возможная оптимизация:** Получать RAW-данные один раз на стороне клиента и фильтровать на фронтенде (потребует нового эндпоинта или режима ответа).

---

#### P3-2: Мёртвый код — `_resolve_and_upsert_entity`

**Файл:** `consistency_manager.py`

Метод `_resolve_and_upsert_entity` является мёртвым кодом, заменённым `_batch_resolve_entities`. Следует удалить во избежание путаницы.

- `backend/app/routers/images.py` — ~33K строк
- `backend/app/routers/reading_sessions.py` — ~41K строк

Эти файлы значительно превышают разумный размер и уже отмечались в аудите от 6 февраля. Не специфично для Entity, но влияет на поддерживаемость.

#### P3-4: `lazy="raise"` используется последовательно

**Файлы:** Все entity-модели (`entity.py`, `entity_mention.py`, `entity_event.py`, `entity_relationship.py`)

Все ORM-связи используют `lazy="raise"`, что **корректно для async SQLAlchemy**. Это предотвращает случайную синхронную lazy-загрузку в асинхронных контекстах. Хорошее решение.

## 4. Оценка соответствия best practices

| Категория | Текущее состояние | Best Practice | Разрыв |
|-----------|-------------------|---------------|--------|
| **Спойлерная защита** | 7 точек фильтрации, 4 сломаны | Все должны использовать одно индексирование | P1-1 исправляет все 4 |
| **Паттерн upsert** | ON CONFLICT заменяет JSONB | LEAST/GREATEST для скаляров, `\|\|` для массивов | P0-1, P2-1 |
| **Advisory locks** | SHA256-based `pg_advisory_xact_lock` | Корректный паттерн для распределённого создания сущностей | ✅ Хорошо |
| **Стратегия кеша** | «Cache RAW, фильтровать по запросу» | Рекомендуется для представлений, меняющихся по главам | ✅ Хорошо |
| **Инвалидация кеша** | Отсутствует после конвейера | Обязательна после записи | P1-2 |
| **Async ORM** | `lazy="raise"` везде | Предотвращает синхронную загрузку в async | ✅ Хорошо |
| **Сопоставление имён** | `casefold()` для Python, колонка `name_lower` | Unicode-aware, locale-независимо | ✅ Хорошо |
| **LLM Retry** | Tenacity 3x exponential backoff | Стандарт для LLM API | ✅ Хорошо |
| **LLM структурированный вывод** | Pydantic response_schema | Гарантирует парсируемые ответы LLM | ✅ Хорошо |
| **Дедупликация сущностей** | Fuzzy + LLM merge | Хороший двухэтапный подход | Порог P2-4 |
| **Фронтенд-спойлер** | CFI + фоллбэк по главе | Корректное прогрессивное улучшение | ✅ Хорошо |
| **Фронтенд-кеш** | TanStack Query, stale 1ч | Подходит для entity-данных | P3-1 (незначительно) |
| **Безопасность миграций** | Alembic с корректными up/down | Стандарт для FastAPI | ✅ Хорошо |
| **Типобезопасность** | Выравнивание Pydantic ↔ TypeScript | Опциональные поля различаются | P3 (незначительно) |
