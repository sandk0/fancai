## Резюме

Архитектура системы Entity Wiki выстроена грамотно — паттерн «кэшируем RAW, фильтруем per-request» в entity_service.py хорошо спроектирован, а фронтенд корректно использует 1-индексные номера глав из упоминаний. Однако **в 4 из 7 точек спойлер-фильтрации обнаружен баг сдвига на единицу (off-by-one)**, вызванный одной строкой в `book_tasks.py:575`, которая использует 0-индексный `enumerate(chapters)`, тогда как вся остальная система ожидает 1-индексные номера глав. Кроме того, конструкция `ON CONFLICT DO UPDATE` в consistency_manager.py **никогда не обновляет `first_mention_chapter`**, что является вероятной первопричиной ранее зафиксированного симптома «сущности залочены на последней главе». Баг с Python-truthiness молча теряет визуальные описания для главы 0. В совокупности эти проблемы создают систему защиты от спойлеров, которая внешне работает, но раскрывает информацию на одну главу раньше и некорректно отслеживает первое появление сущностей.

## 1. Карта сквозного потока данных

### 1.1 EPUB → Парсинг глав (1-индексация)

```
book_parser.py:569  enumerate(flat_toc, start=1)     → chapter_num = 1,2,3...
book_parser.py:685  len(chapters) + 1                 → chapter_num = 1,2,3...
book_parser.py:849  chapter_number = 1; +=1           → chapter_num = 1,2,3...
                          ↓
book_service.py:105 Chapter.chapter_number = chapter_data.number  → БД: 1-индексация ✅
```

### 1.2 Пайплайн обработки глав (0-индексация — БАГ)

```
book_tasks.py:575   enumerate(chapters)               → idx = 0,1,2...  ← ПЕРВОПРИЧИНА
                          ↓
book_tasks.py:411   chapter_index=idx                  → ConsistencyManager получает 0-индексное
book_tasks.py:424   chapter_number=idx                 → EntityEvent получает 0-индексное
                          ↓
consistency_manager.py:94   f"[Глава {chapter_index}]" → маркеры visual_summary: 0-индексация
consistency_manager.py:384  first_mention_chapter=idx   → Entity.first_mention_chapter: 0-индексация
consistency_manager.py:385  aliases_with_reveal[].reveal_chapter = idx → 0-индексация
```

### 1.3 LLM-синтез (наследует 0-индексацию)

```
entity_synthesis_service.py  → Читает events с chapter_number=0,1,2...
                             → Генерирует biography_milestones с up_to_chapter на основе этих данных
                             → Milestones наследуют 0-индексную нумерацию
```

### 1.4 Слой кэширования и фильтрации

```
entity_service.py            → _build_raw_network_cache(): загружает все данные, без привязки к главе
                             → Redis ключ: book:{book_id}:entity_network_raw_v5
                             → _apply_chapter_filter(raw, current_chapter):
                                  _filter_events_by_chapter()        ← 0-индексные events vs 1-индексный current_chapter
                                  _get_current_milestone()           ← 0-индексные milestones vs 1-индексный
                                  _filter_aliases_from_raw()         ← 0-индексный reveal_chapter vs 1-индексный
                                  _process_visual_summary()          ← 0-индексные [Глава N] vs 1-индексный
```

### 1.5 Фронтенд: запрос и отображение (1-индексация)

```
useChapterManagement.ts:36   useState<number>(1)                → начинает с 1
useChapterManagement.ts:59   Math.max(1, spineIndex + 1)        → гарантирует 1-индексацию
                          ↓
useEntityNetwork.ts:18       EntityService.getNetwork(bookId, currentChapter)  → отправляет 1-индексный
                          ↓
entityUtils.ts:4-16          isEntityMet(): mentions из Chapter.chapter_number → 1-индексация ✅
entityUtils.ts:33-36         isNoteSpoiler(): note.chapter_index из Chapter → 1-индексация ✅
```

### 1.6 Ключевой вывод

Массив **mentions** в EntityDetailSchema формируется через JOIN по `Chapter.chapter_number` (1-индексный), поэтому `isEntityMet()` и `isNoteSpoiler()` работают корректно. Но **events, milestones, aliases, visual_summary** — все проходят через 0-индексный путь `enumerate(chapters)`, что создаёт сдвиг на единицу при сравнении с 1-индексным `current_chapter` фронтенда.

**Итоговый эффект:** Events/aliases/milestones из главы N (0-индексация) фильтруются относительно `current_chapter=N` (1-индексация), поэтому они отображаются на одну главу РАНЬШЕ. Это утечка спойлеров, а не блокировка.

## 3. Находки по приоритетам

### P0 — Критические (повреждение данных / тихая потеря данных)

#### P0-1: ON CONFLICT никогда не обновляет `first_mention_chapter`

**Файл:** `consistency_manager.py:393-400`

```python
stmt = stmt.on_conflict_do_update(
    index_elements=["book_id", "name_lower"],
    set_={
        "entity_metadata": stmt.excluded.entity_metadata,
        "aliases_with_reveal": stmt.excluded.aliases_with_reveal,
        "updated_at": func.now(),
    },
)
```

Когда та же сущность встречается в более поздней главе (типичная ситуация при параллельной обработке), конструкция ON CONFLICT **обновляет только `entity_metadata` и `aliases_with_reveal`**. НЕ обновляются:
- `first_mention_chapter` — остаётся значение, установленное той параллельной задачей, которая первой выиграла гонку
- `visual_summary` — полностью теряется для главы, проигравшей конфликт
- `importance` — залочен на первое встреченное значение

Поскольку `asyncio.gather` обрабатывает все главы параллельно, глава, завершившаяся первой (не обязательно глава 1), выигрывает INSERT. Все последующие главы попадают в ON CONFLICT, и их значения `first_mention_chapter` тихо отбрасываются. **Это вероятная первопричина симптома «сущности залочены на последней главе», описанного в предыдущем аудите.**

**Исправление:** Добавить `first_mention_chapter` в set_ с `LEAST(Entity.first_mention_chapter, excluded.first_mention_chapter)` и объединять (а не заменять) `visual_summary`.

---

#### P0-2: Баг Python-truthiness теряет visual_summary для главы 0

**Файл:** `consistency_manager.py:94`

```python
chapter_marker = f"[Глава {chapter_index}]" if chapter_index else ""
```

Когда `chapter_index=0` (что происходит из-за бага enumerate), `if chapter_index` вычисляется как `False`, и визуальное описание первой главы получает ПУСТОЙ маркер главы. Это означает:
1. Visual_summary первой главы добавляется без маркера
2. `_process_visual_summary()` обрабатывает текст без маркера как «базовый текст» (показывается всегда), полностью обходя защиту от спойлеров

**Исправление:** `if chapter_index is not None` вместо `if chapter_index`.

---

### P1 — Высокий приоритет (утечка спойлеров)

#### P1-1: Сдвиг индекса главы на единицу (первопричина)

**Файл:** `book_tasks.py:575`

```python
results = await asyncio.gather(
    *(process_chapter_safe(idx, chapter.id) for idx, chapter in enumerate(chapters)),
    ...
)
```

`enumerate(chapters)` порождает `idx=0,1,2,...`, тогда как `Chapter.chapter_number` в БД — `1,2,3,...`. Этот 0-индексный `idx` распространяется в:
- `book_tasks.py:411` → `chapter_index=idx` → ConsistencyManager
- `book_tasks.py:424` → `chapter_number=idx` → EntityEvent
- `consistency_manager.py:94` → маркеры visual_summary `[Глава N]`
- `consistency_manager.py:384` → `first_mention_chapter=idx`
- `consistency_manager.py:385` → `aliases_with_reveal[].reveal_chapter=idx`

**Исправление:** `enumerate(chapters, start=1)` или использовать `chapter.chapter_number` из объекта БД.

---

#### P1-2: Redis-кэш сети сущностей не инвалидируется после обработки книги

**Файл:** `book_tasks.py` (секция инвалидации кэша, ~строка 850+)

После завершения полного пайплайна извлечения сущностей, `book_tasks.py` инвалидирует паттерны кэша `user:*:books:*`, но НЕ инвалидирует `book:{book_id}:entity_network_raw_v5`. Это означает:
- Если кэш был заполнен до переобработки, устаревшие данные сущностей сохраняются
- Пользователи видят старые данные сущностей до истечения TTL Redis или ручной инвалидации

**Исправление:** Добавить `await redis.delete(f"book:{book_id}:entity_network_raw_v5")` после завершения пайплайна.

### P2 — Средний приоритет (качество данных / UX)

#### P2-1: ON CONFLICT заменяет вместо слияния JSONB-полей

**Файл:** `consistency_manager.py:396-397`

```python
set_={
    "entity_metadata": stmt.excluded.entity_metadata,
    "aliases_with_reveal": stmt.excluded.aliases_with_reveal,
}
```

Когда параллельные воркеры глав создают ту же сущность, конструкция ON CONFLICT **заменяет** `entity_metadata` и `aliases_with_reveal` целиком, а не объединяет. Если глава 3 добавляет псевдоним «Гарри», а глава 5 — «Мальчик-который-выжил», то тот воркер, который завершится последним, перезапишет псевдонимы другого.

**Исправление:** Использовать PostgreSQL-оператор `jsonb_concat` или `||` для слияния массивов:
```sql
aliases_with_reveal = entities.aliases_with_reveal || excluded.aliases_with_reveal
```

---

#### P2-2: Подсветка имён сущностей использует регистрозависимый поиск

**Файл:** `useEntityNameHighlighting.ts:113`

```typescript
const idx = text.indexOf(term.text);
```

`String.indexOf()` регистрозависим. Если имя сущности — «Гарри Поттер», а в тексте «ГАРРИ ПОТТЕР» или «гарри поттер», подсветка не сработает. Это особенно проблематично для русского текста, где регистр часто варьируется.

**Исправление:** Использовать `text.toLowerCase().indexOf(term.text.toLowerCase())` или локаль-зависимый регистронезависимый поиск.

Фронтенд фильтрует события по главе на уровне UI, но бэкенд уже фильтрует события в `_filter_events_by_chapter()`. Это избыточно, но не вредно — лишь расходует вычислительные ресурсы.

Порог 0.85 для `SequenceMatcher` пропускает типичные неполные совпадения имён, например «Гарри» vs «Гарри Поттер» (ratio ~0.57). Это было выявлено ещё в аудите 6 февраля, но остаётся неисправленным.

### P3 — Низкий приоритет (производительность / качество кода)

#### P3-1: Ключ TanStack Query включает `currentChapter`

**Файл:** `useEntityNetwork.ts:8-11`

```typescript
export const entityNetworkQueryKey = (bookId: string, currentChapter?: number) =>
    currentChapter != null
        ? ['book', bookId, 'entities', currentChapter]
        : ['book', bookId, 'entities'];
```

Поскольку бэкенд выполняет фильтрацию по главам, каждая смена главы создаёт новую запись в кэше. Для книги из 50 глав это 50 отдельных закэшированных ответов сети. Учитывая бэкенд-паттерн «кэшируем raw, фильтруем per-request», это by design (каждая глава действительно возвращает разные данные), но это означает:
- 50 сетевых запросов за полное прочтение
- Отсутствие повторного использования клиентского кэша между главами

**Потенциальная оптимизация:** Загружать raw-данные один раз на клиенте и фильтровать на фронтенде (потребует новый эндпоинт или режим ответа).

#### P3-2: Мёртвый код — `_resolve_and_upsert_entity`

**Файл:** `consistency_manager.py`

Метод `_resolve_and_upsert_entity` является мёртвым кодом, вытесненным `_batch_resolve_entities`. Следует удалить для снижения путаницы.

#### P3-3: Размеры файлов роутеров

- `backend/app/routers/images.py` — ~33K строк
- `backend/app/routers/reading_sessions.py` — ~41K строк

#### P3-4: `lazy="raise"` используется консистентно

**Файлы:** Все модели сущностей (`entity.py`, `entity_mention.py`, `entity_event.py`, `entity_relationship.py`)

Все ORM-relationship используют `lazy="raise"`, что **корректно для async SQLAlchemy**. Это предотвращает случайную синхронную ленивую загрузку в асинхронных контекстах. Хорошо сделано.
