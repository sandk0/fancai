# Отчет об архитектуре обработки книг и формировании карточек сущностей (Fancai Vibe)

**Дата:** 24.01.2026
**Версия системы:** v16 (с исправлением отношений `gemini_extractor`)
**Назначение:** Техническая документация для Frontend-команды перед внедрением Entity Cards.

## 1. Пайплайн Обработки (The Pipeline)

Процесс запускается асинхронно через Celery (`backend/app/core/tasks.py`).

### Этапы выполнения (`process_book_task`):
1.  **Инициализация (0%)**:
    *   Создается запись в Redis для отслеживания прогресса.
    *   Загружается текст книги (EPUB/FB2).
2.  **Парсинг Глав (0-80%)**:
    *   `GeminiDirectExtractor` разбивает текст на чанки (по ~100k символов с перекрытием).
    *   **Параллельность**: Используется `asyncio.Semaphore(3)` для одновременной обработки до 3 чанков через Gemini API.
    *   **Извлечение**: Из каждого чанка достаются `Descriptions` (сцены), `Entities` (персонажи) и `Relationships` (связи).
    *   **Сохранение**: Данные сохраняются в БД *поглавно*.
    *   **Прогресс**: WebSocket-событие отправляется после каждой главы.
3.  **Оптимизация / Reduce Phase (85%)**:
    *   `ConsistencyManager` загружает *все* найденные сущности.
    *   Отправляет единый список в Gemini с просьбой: "Объедини дубликаты (Гарри = Поттер) и удали мусор (Importance < 7)".
    *   Выполняет `DELETE` и `UPDATE` в базе данных.
4.  **Построение Графа (90%)**:
    *   `GraphService` строит граф в памяти (NetworkX).
    *   Рассчитывает PageRank для уточнения важности (Importance) персонажей.
5.  **Финализация (95-100%)**:
    *   Генерация Master References (портретов) для топ-персонажей через Imagen (если включено).
    *   Статус книги меняется на `Completed`.

## 2. Формирование Данных Сущности (Data Origin)

Откуда берутся поля для UI карточки сущности:

| Поле UI | Источник данных (БД) | Механизм формирования |
| :--- | :--- | :--- |
| **Имя** | `Entity.name` | Извлекается из текста. Может быть изменено на canonical name во время Reduce-фазы (слияния дубликатов). |
| **Тип** | `Entity.type` | `CHARACTER`, `LOCATION`, `OBJECT`. Определяется LLM. |
| **Важность** | `Entity.importance` (1-10) | Первично от LLM, затем корректируется алгоритмом PageRank (чем больше связей, тем выше важность). |
| **Портрет (Саммари)** | `Entity.visual_summary` | Текстовое описание внешности. *Аггрегируется LLM*: при слиянии сущностей берется самое длинное и детальное описание. |
| **Изображение (Аватар)** | `Entity.master_portrait_url` | URL сгенерированного изображения (файл в `/api/v1/images/file/...`). |
| **Связи** | `EntityRelationship` | Создаются на этапе парсинга. **Важно:** Текстовое описание связи лежит в `relationship_metadata['context']`. |

### Нюансы связей (Relationships):
*   **Контекст**: Описание *почему* они связаны (например "А ученик Б") лежит в JSON-поле `entity_relationships.relationship_metadata` под ключом **`context`**.
    *   *Ранее была ошибка поиска в поле `description`, исправлено 24.01.*
*   **Вес (Strength)**: Поле `weight` часто равно `0`. Причина: текущий промпт не требует жесткой шкалы 1-10. Для UI лучше использовать наличие связи как факт, не опираясь на толщину линии.

### Описания (Descriptions / Scenes):
Внизу карточки выводятся "Key Scenes".
*   **Источник**: Таблица `Description`.
*   **Фильтрация**: `WHERE type='CHARACTER' AND entities_mentioned ILIKE '%Name%'`.
*   **Суть**: Это *не* чистое описание внешности. Это сырые куски текста (абзацы) из книги, где этот персонаж что-то делает или упоминается.
*   **Связь**: Поле `entities_mentioned` — это простая строка (Text), не массив UUID. Поиск идет стринговым сравнением (`ILIKE`), что может давать ложные срабатывания (например, если персонажа зовут "Роза", найдутся и цветы).

## 3. Фаза Оптимизации (Reduce Phase Issue)

Метод `consistency_manager.optimize_book_entities` выполняет слияние.
**Риск для Фронтенда (Дубликаты):**
*   Логика слияния полагается на один вызов LLM со списком всех имен.
*   Если список огромный (1000+ персонажей), он может быть обрезан, или LLM пропустит дубликаты.
*   **Результат**: В базе могут остаться две сущности: "Геральт" и "Ведьмак" с разными ID.
*   **Рекомендация UI**: Быть готовым показать несколько карточек или группировать их, если это критично. В текущей версии API отдает их как разные объекты.

## 4. Расход Токенов и Лимиты

Оценка для средней книги (500,000 символов, ~125,000 токенов):

1.  **Chunking**:
    *   Размер чанка: ~20-25k токенов (100k символов).
    *   Количество чанков: ~5-6 шт.
    *   Расход на чтение: 125,000 токенов (Input).
2.  **Output (JSON)**:
    *   На каждый чанк ~2-4k токенов ответа (списки сущностей, описаний).
    *   Всего Output: ~20,000 токенов.
3.  **Reduce Phase**:
    *   Посылает список всех сущностей обратно (Input ~10-20k токенов).
4.  **Итого на книгу**: ~150,000 - 200,000 токенов.

**Модель**: Используется `gemini-3-flash-preview`.
*   Контекстное окно большое (1M+), проблем с размером чанка нет.
*   Цена крайне низкая по сравнению с GPT-4.
*   Скорость: высокая (Flash модель).

## 5. Известные проблемы (Known Issues)

При разработке UI обдумайте следующее:

1.  **Strength = 0**: Не используйте толщину линий в графе визаулизации, если `weight=0`. Рисуйте пунктир или стандартную линию.
2.  **"Мусорные" сцены**: В списке описаний могут попадаться скучные фрагменты ("Он встал и вышел"). Это нормально для текущего NLP-пайплайна. Если нужно скрыть — используйте только те, где `confidence_score > 0.8`.
3.  **Дубликаты**: Если API вернул два "Геральта", фронтенд покажет два. (Бэкенд-задача: улучшить Prompt в `consistency_manager`).
4.  **Отсутствие Аватара**: Если `master_portrait_url` is NULL, показывайте плейсхолдер (генерация картинок может быть отключена или упасть по квоте).
