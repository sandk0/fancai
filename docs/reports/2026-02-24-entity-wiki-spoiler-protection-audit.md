## Резюме

Первая версия этого аудита (v1 от 24.02.2026) содержала **6 ошибочных или сильно искажённых выводов** из 23. Данная версия исправляет эти ошибки на основе:

- Git-истории (git log, git show, git blame) для каждого оспариваемого решения
- 13 ранее написанных отчётов (2026-01-23 — 2026-02-06) об Entity Wiki
- Проектной документации (`docs/plans/2026-02-06-entity-wiki-design.md`, `2026-02-07-entity-wiki-implementation.md`)
- Прямого чтения кода с точными номерами строк

**Итог после верификации:** Из 23 выводов v1:
- **12 подтверждены** (часть с уточнениями)
- **5 переклассифицированы** (изменён приоритет или формулировка)
- **6 отозваны** как ошибочные

**Верифицированные ключевые находки:**
1. **P0-1:** Баг в реализации кеширования — cache HIT возвращает данные без фильтрации (дизайн предусматривал фильтрацию, но реализация её пропустила)
2. **P1-1:** `maxChapterReached` не имеет серверного поля — при перезагрузке страницы high-water mark теряется
3. **P1-2:** `entityNetworkQueryKey` включает `currentChapter` — мерцание UI при каждой смене главы (новая находка, ранее не описанная)
4. **P1-3:** `@lru_cache` на instance method `_normalize_name` — кеш бесполезен + утечка памяти (новая находка)

### Причины ошибок

1. **Не проверил git-историю** — назвал осознанные решения «багами»
2. **Не прочитал существующие отчёты** — 13 отчётов уже анализировали те же проблемы
3. **Поверхностный grep** — пропустил CASCADE, rate-limiting, CSS-защиту аватаров
4. **Доверился предположениям Oracle** вместо верификации каждого вывода

## Верифицированные проблемы (P0)

### P0-1. Реализация кеширования расходится с проектным дизайном

**Верификация:** ✅ ПОДТВЕРЖДЕНО с уточнением механизма  
**Источник:** `entity_service.py:144-148`, коммит `f67234a`, дизайн-документ `2026-02-06-entity-wiki-design.md:373-401`  
**Ранее описано:** Нет — **новая находка** (ни один из 13 отчётов не выявил этот конкретный баг)

**Проектный дизайн (docs/plans/2026-02-06-entity-wiki-design.md, раздел 5.1):**
```
Стратегия: "RAW Cache + On-the-fly Filtering"
1. Кешировать RAW данные (все milestones, events, aliases), без фильтрации по главе
2. При каждом запросе: filter_by_chapter(raw_data, current_chapter=effective_chapter)
```

**Фактическая реализация (entity_service.py:144-148):**
```python
cache_key = f"book:{book_id}:entity_network_raw_v4"  # v4 RAW cache (no chapter filter)
cached_data = await cache_manager.get(cache_key)
if cached_data:
    return EntityNetworkResponse.model_validate(cached_data)  # ← Возврат БЕЗ фильтрации!
```

**Проблема:** На **cache HIT** данные возвращаются напрямую без вызова `_build_network_response()`. Параметр `current_chapter` полностью игнорируется. На **cache MISS** фильтрация вызывается, но затем **уже отфильтрованный** результат кешируется как якобы «raw». В итоге:
- Первый пользователь на главе 5 создаёт кеш с данными, отфильтрованными до 5 главы
- Второй пользователь на главе 1 получает из кеша данные с информацией до главы 5 → **спойлер**
- Третий пользователь на главе 20 получает данные, обрезанные до 5 главы → **неполные данные**

**Это баг реализации**, а не архитектурный дефект. Дизайн правильный (cache raw → filter per-request), но шаг 2 не был реализован на пути cache HIT.

**Рекомендация:** Добавить вызов фильтрации после `cache_manager.get()`. Убедиться, что в кеш сохраняются RAW данные до фильтрации, а не после.

**Сложность:** Средняя  
**Влияние:** Критическое — cross-user spoiler leakage

### P0-2. N+1 запрос в эндпоинте recap (ограниченный)

**Верификация:** ✅ ПОДТВЕРЖДЕНО с уточнением масштаба  
**Источник:** `routers/books/entities.py:120-140`  
**Ранее описано:** Частично (отчёт 2026-01-25 упоминал N+1 в entity_service, но не в recap)

**Проблема:** Эндпоинт выполняет 1 запрос на список + 1 запрос на каждую сущность в цикле:
```python
entities_q = select(Entity).where(...).order_by(Entity.importance.desc()).limit(5)  # запрос 1
for entity in top_entities:
    event_q = await db.execute(select(EntityEvent).where(...))  # запросы 2-6
```

**Уточнение:** Цикл **ограничен 5 итерациями** (`.limit(5)`), поэтому всего 6 запросов, а не «100+» как заявлялось в v1. Импорт `selectinload` на строке 117 не используется (мёртвый код), что подсказывает, что кто-то начал оптимизировать, но не завершил.

**Рекомендация:** Заменить цикл на одну запрос с `selectinload(Entity.events)` или window function.

**Сложность:** Короткая  
**Влияние:** Среднее (6 запросов, не катастрофа, но легко оптимизируется)

## Верифицированные проблемы (P1)

### P1-1. `maxChapterReached` не имеет серверного хранилища

**Верификация:** ✅ ПОДТВЕРЖДЕНО  
**Источник:** `EpubReader.tsx:218-221`, модель `ReadingProgress` в `book.py:260-329`  
**Ранее описано:** Нет — **новая находка**

**Проблема:** `maxChapterReached` вычисляется на клиенте:
```typescript
const maxChapterReached = useMemo(() => {
    const savedChapter = book.reading_progress?.current_chapter || 1;
    return Math.max(currentChapter, savedChapter);
}, [currentChapter, book.reading_progress]);
```

Модель `ReadingProgress` содержит только `current_chapter` (строка 287), а не максимальный. Если пользователь прочитал до главы 20, вернулся к главе 5, и затем перезагрузил страницу:
- `savedChapter` = 5 (последняя сохранённая позиция)
- `currentChapter` = 5
- `maxChapterReached` = 5 (high-water mark 20 потерян)

Коммит `9454af5` (29 янв) добавил `maxChapterReached`, но без серверной персистенции.

**Рекомендация:** Добавить `max_chapter_reached INT` в `ReadingProgress`. Обновлять server-side при `current_chapter > max_chapter_reached`.

**Сложность:** Короткая (~полдня)  
**Влияние:** Высокое — спойлер-гейт теряет high-water mark

### P1-2. `entityNetworkQueryKey` включает `currentChapter` → мерцание UI

**Верификация:** ✅ ПОДТВЕРЖДЕНО  
**Источник:** `useEntityNetwork.ts`  
**Ранее описано:** Нет — **новая находка** (ни один из 13 отчётов)

**Проблема:** TanStack Query key содержит `currentChapter`. При каждой смене главы (пользователь переворачивает страницу) — cache miss → refetch → loading state → мерцание панели сущностей.

**Рекомендация:** Убрать `currentChapter` из query key. Запрашивать полный граф один раз, фильтровать на клиенте. Это устранит мерцание — самую раздражающую UX-проблему.

**Сложность:** Быстро (1 строка)  
**Влияние:** Высокое — UX читалки

### P1-3. `@lru_cache` на instance method `_normalize_name`

**Верификация:** ✅ ПОДТВЕРЖДЕНО  
**Источник:** `entity_service.py:36-40`  
**Ранее описано:** Нет — **новая находка**

```python
@lru_cache(maxsize=1000)
def _normalize_name(self, name: str) -> str:
    if not name:
        return ""
    return name.lower().strip().replace("ё", "е")
```

`EntityService` создаётся заново для каждого запроса через `get_entity_service()` (строка 552). Каждый новый `self` — новый ключ кеша. `lru_cache` бесполезен. Хуже — ссылка на `self` (содержащий `AsyncSession`) остаётся в кеше, предотвращая GC.

**Рекомендация:** Сделать `@staticmethod` (функция не использует `self`) или вынести на уровень модуля.

**Сложность:** Быстро  
**Влияние:** Среднее — утечка памяти + бесполезный overhead

### P2-6. `isEntityMet` fail-open — дискуссионное архитектурное решение

**Верификация:** Переклассифицировано из P0-2 в P2 (дискуссионный вопрос, не баг)

**История решения:**
- **24 янв, коммит `5f2eb6e`:** `isEntityMet` возвращал `false` для пустых mentions (strict)
- **24 янв, коммит `ac40b26`:** Изменён на `true` с комментарием: «Fail-Open Strategy: Better to show a spoiler than an empty screen»
- **25 янв, отчёт deep-analysis:** Оценён как «7/10, правильное решение при неполных данных»
- **26 янв, коммит `bfb7c3e`:** Рефакторинг сохранил `return true`

**Суть дилеммы:** При пустом массиве `mentions` (backend не заполнил данные):
- `return false` → все сущности скрыты, drawer бесполезен → **плохой UX**
- `return true` → сущности видны, но потенциально содержат спойлеры → **потенциальный спойлер**

Текущее решение (fail-open) — **осознанный компромисс**, а не баг. Альтернатива — исправить backend, чтобы `mentions` никогда не был пустым, а не менять поведение frontend.

**Рекомендация:** Вместо изменения дефолта — обеспечить, чтобы backend всегда заполнял `mentions` при обработке книги. Fail-open правильнее fail-closed для данного контекста.
