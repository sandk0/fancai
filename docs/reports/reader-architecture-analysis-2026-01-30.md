# Глубокий архитектурный анализ читалки Fancai

**Дата:** 30 января 2026  
**Статус:** Анализ завершен, требуется решение по PWA стратегии

---

## 1. Верификация выводов первичного аудита

### 1.1. Подтвержденные критические уязвимости
В ходе глубокого анализа (Deep Dive) подтверждены следующие выводы из отчета `reader-comprehensive-audit-2026-01-30.md`:

1.  **PWA Guard на Desktop:**
    *   **Факт:** Хук `usePWAResumeGuard` действительно не имеет проверки типа устройства.
    *   **Влияние:** Любое переключение вкладки на 1.5+ секунды на десктопе триггерит логику "восстановления", которая принудительно размонтирует `EpubReader`.
    *   **Последствие:** Разрыв активной сессии чтения, потеря локального стейта (например, выделения текста), визуальный "блик" (спиннер).

2.  **Stale Cache Problem:**
    *   **Факт:** В `queryClient.ts` установлен глобальный `staleTime: 5 * 60 * 1000` (5 минут).
    *   **Влияние:** При пересоздании компонента (например, после срабатывания PWA Guard) React Query возвращает кешированные данные "активной сессии", даже если она была закрыта на сервере (например, по таймауту или cleanup-скриптом).
    *   **Последствие:** Клиент пытается обновить ID сессии, которой уже нет → получает 400 → входит в бесконечный цикл ошибок, так как не знает, что данные протухли.

### 1.2. Опровержения и уточнения
*   **Global Retry Logic:** Анализ `queryClient.ts` показал, что глобальная конфигурация **НЕ** делает ретраи для 400-х ошибок.
    *   *Вывод:* "Бесконечный цикл" ошибок в консоли — это не вина React Query, а результат работы `setInterval` внутри `useReadingSession`, который не останавливается при получении фатальной ошибки (400 Bad Request).

## 2. Новые находки (Deep Dive Findings)

### 2.1. Конфликт данных (Data Consistency Split)
Обнаружена фундаментальная проблема в архитектуре сохранения прогресса. Данные пишутся в две **разные, слабо связанные** сущности:

| Хук | Эндпоинт | Таблица БД | Что пишет |
|-----|----------|------------|-----------|
| `useProgressSync` | `POST /api/v1/books/{id}/progress` | `reading_progress` | CFI, %, Глава |
| `useReadingSession` | `PUT /reading-sessions/{id}/update` | `reading_sessions` | %, Длительность |

**Риск:** Рассинхронизация (Split Brain).
Если `useReadingSession` падает с ошибкой (например, сессия протухла), но `useProgressSync` продолжает успешно работать:
1.  Пользователь видит, что прогресс сохраняется (зеленая галочка).
2.  В статистике (Reading Streak, Time Read) это время **не учитывается**.
3.  При восстановлении позиции может возникнуть конфликт: "Последняя сессия была на 10%, а прогресс на 15%".

### 2.2. "Зомби-сессии"
Хук `useReadingSession` использует `setQueryData` для ручного управления кешем, но **никогда** не делает `invalidateQueries` для проверки актуальности данных с сервером.
*   *Результат:* Если сервер закроет сессию (например, фоновый worker очистит старые сессии), клиент никогда об этом не узнает, пока не попытается сделать update и не получит ошибку.

## 3. Архитектурные риски (Hook Spaghetti)
Компонент `EpubReader` использует более 22 хуков. Обнаружена сильная связность через неявное состояние:
*   `useReadingSession` зависит от `progress` (из `useCFITracking`).
*   `useProgressSync` зависит от `currentCFI` (из `useCFITracking`).
*   `usePWAResumeGuard` управляет жизненным циклом всего дерева компонентов.

**Проблема:** Логика размазана. Жизненный цикл ("Открыл книгу" -> "Читаю" -> "Свернул" -> "Развернул") управляется тремя разными независимыми механизмами (`usePWAResumeGuard`, `useRenditionHealthGuard`, `useReadingSession`), которые конфликтуют друг с другом (reload vs unmount vs pause).

## 4. Стратегический вопрос (PWA Strategy)

Я подготовил план доработок, но перед его финализацией мне нужно твое решение по стратегии PWA, так как это влияет на объем работ.

**Ситуация:**
Текущий механизм `PWA Resume Guard` (размонтирование ридера для "безопасного" восстановления) слишком агрессивен. Он был создан для решения проблем iOS (выгрузка памяти), но работает везде, ломая UX на десктопах.

**Варианты решения:**

1.  **Вариант А: "Адаптивный" (Рекомендуемый для качества)**
    *   Оставить Guard, но сделать его "умным":
    *   На Desktop: Полностью отключить (return early).
    *   На Mobile: Использовать Overlay (шторку) вместо размонтирования компонента.
    *   *Плюсы:* Идеальный UX везде. Решает проблему потери стейта.
    *   *Минусы:* Чуть сложнее в реализации (нужен детектор устройств).

2.  **Вариант Б: "Хард-офф" (Быстрый фикс)**
    *   Просто выключить Guard везде, где не `display-mode: standalone`.
    *   *Плюсы:* 5 минут работы.
    *   *Минусы:* Если пользователь откроет сайт в мобильном Safari (не PWA), он снова словит баги с вылетом epub.js.

3.  **Вариант В: "Тотальный рефакторинг" (Долгосрочный)**
    *   Выкинуть Guard. Переписать `EpubReader` так, чтобы он умел переживать потерю контекста без перезагрузки (восстанавливать `rendition` "на лету").
    *   *Плюсы:* Архитектурно правильно.
    *   *Минусы:* Очень дорого и долго (недели работы).

**Мой вопрос:** Какой вариант выбираем? Я рекомендую **Вариант А** как баланс между качеством и скоростью. Жду твоего решения, чтобы включить его в план.
