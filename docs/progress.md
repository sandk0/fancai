### 3. Дефект прогресса чтения — найден живым прогоном e2e

`GET /books/{id}/progress` отвечал 500: «Multiple rows were found when one
or none was required». У `reading_progress` не было уникального ограничения
на `(user_id, book_id)`, а сервис писал через read-then-insert. Читалка
сохраняет позицию пачками, поэтому два одновременных запроса оба не
находили строку и оба вставляли свою. **Дубль оставался навсегда**, и после
него прогресс книги нельзя было ни записать, ни прочитать.

Второй, более тихий отказ: `max_chapter_reached` монотонен, на нём держится
спойлерный гейт глоссария. Read-modify-write без блокировки позволял двум
сохранениям прочитать одно старое значение — поздний commit занижал максимум,
то есть закрывал читателю уже открытые главы.

Фикс из трёх частей: миграция `g1h2i3j4k5l6` (схлопывает дубли, ставит
`uq_reading_progress_user_book`), `INSERT … ON CONFLICT DO NOTHING`
и `SELECT … FOR UPDATE` в сервисе.

Round-trip миграции на dev-БД: две посеянные строки `3|42|max=9`
и `2|7|max=4` схлопнулись в одну — `2|7|max=9`, то есть свежая позиция
с сохранённым максимумом главы; повторная вставка отвергается
`duplicate key value violates unique constraint`; downgrade снимает
ограничение. Регрессионный тест — восемь параллельных сохранений
из независимых сессий; **мутация**: со снятым `.with_for_update()` он падает
`max_chapter_reached обязан быть монотонным: ожидался 8, получен 7`.

### 4. E2E (§2.1) — переписан, но приёмка не закрыта

**На входе:** 25 passed / 78 failed на chromium (103 теста).
**Сейчас:** после слияния дубликатов 79 тестов на проект.
Chromium в изоляции — **77 passed / 2 skipped / 0 failed**.
Полная матрица пяти проектов — **313 passed / 65 failed / 10 skipped /
7 did not run** (395) за 19 минут. По проектам: chromium 1, firefox 3,
Mobile Chrome 8, webkit 25, Mobile Safari 28. Семь «did not run» — это
serial-блок auth, свёрнутый ранним падением на Mobile Safari
(там 42 passed / 28 failed / 2 skipped / 7 did not run).
Самая частая причина — одна: 34 падения с «панели читалки не раскрылись».
Разбор — в конце раздела.

Причин было три, и ни одна не решалась добавлением `data-testid`.

**4.1. Не было подготовленной среды.** `backend/scripts/e2e_fixture.py`
плюс `globalSetup`/`globalTeardown`. Правила, ради которых он написан
(прошлая попытка была удалена именно за их нарушение):

- аккаунты живут в пространстве имён прогона
  `e2e-run-<run_id>.…@fancai.ru`, поэтому **ни один существующий
  не трогается вовсе** — провенанс восстанавливать не из чего; совпадение
  имени считается аварией и останавливает setup;
- удаляется только созданное этим прогоном и только по ID. Разность
  снимков БД как критерий удаления отвергнута: она снесла бы параллельную
  запись владельца. Снимок — только для сверки, неопознанный остаток
  красит прогон, но не удаляется;
- setup атомарен: state пишется **до** commit, при сбое БД откатывается
  и скопированные файлы удаляются; повторный setup поверх живого state
  отвергается;
- книга копируется целиком — строка, главы и сам файл.
  `BookService.delete_book` сносит файл с диска, и спека удаления
  на общем `file_path` стоила бы единственного реального EPUB в dev;
- на каждый parallel-слот — свои аккаунт, книга, подписка, сущность,
  два описания и одна картинка. Внутри проекта четыре воркера идут
  одновременно, а спека удаления удаляет по-настоящему — с общей книгой
  первый же прошедший delete оставлял бы читалку и галерею без данных.

**Изоляция по слоту, но не по проекту — главный незакрытый дефект среды,
и матрица это доказала.** Playwright гоняет браузерные проекты
**последовательно**, а фикстура ключуется только по `parallelIndex`,
поэтому следующий проект получает того же пользователя, ту же книгу
и ту же сессию. Прогресс чтения и закладки, оставленные chromium, видит
Mobile Chrome.

Раньше здесь стояло «на текущие падения это не влияет» — **утверждение
снято как опровергнутое**. Mobile Chrome даёт 8 падений, и первое из них —
`books.spec` не находит карточку книги фикстуры, после чего каскадом
сыплется читалка. Это ровно картина переиспользования.

**Следующий шаг, названный явно:** заводить книгу и сессию на пару
`(project.name, parallelIndex)`. Книга — прямым клонированием, как сейчас.
С сессией сложнее: двадцать реальных входов не пройдут лимит
в 10 запросов в минуту на IP, а собирать `storageState` вручную из
самодельного JWT — значит обойти настоящий путь входа и потерять
достоверность. Развилку решать отдельно, на свежую голову; в этой сессии
она не бралась сознательно, чтобы не менять фикстуру без прогона матрицы.

Текст описаний берётся **дословно из главы**: `useDescriptionHighlighting`
ищет `desc.content` в отрисованном тексте, выдуманная фраза не подсветится.
Файл картинки кладётся в `/app/storage/generated_images` — каталог,
из которого отдаёт `images.py:66`; и `image_url` заполняется явно, потому
что API отдаёт `image.image_url or ""` и путь сам не строит.

**4.2. Спеки описывали не то приложение.** Проверено по коду:

| Ожидание спеки | Как на самом деле |
| --- | --- |
| `/reader/:id` | `/book/:id/read` |
| кнопки `reader-next-page` / `reader-prev-page` | их нет; на десктопе листает клавиатура, на мобиле — тап по краю, обработчик висит на документе iframe |
| `reader-bookmark-button` в шапке | закладка ставится из меню выделения, и не одним кликом: «Закладка» раскрывает редактор заметки, запись уходит по «Сохранить» |
| тема и шрифт в сторе `fancai-reader` | `app-theme` и `epub_reader_font_size` |
| CFI в `localStorage.last_cfi` | позиция хранится на сервере |
| первый экран книги — текст | обложка, `<svg class="cover-svg">` без единого абзаца |
| `/books/:id/images`, `/users/me/subscription`, `/books/:id/descriptions` | `/book/:id/images`, `/users/subscription`, `/books/:id/chapters/:n/descriptions` |

**4.3. Ложный зелёный.** В `image-generation.spec.ts` было девять
утверждений вида `expect(x || true).toBe(true)` — упасть они не могут, —
и поиск подсветок в родительском документе, хотя текст книги в iframe.
Спека переписана на реальные ответы API. Настоящая генерация не
запускается: это платный вызов и стоп-точка.

**Удалены два дубликата.** `auth-journey.spec.ts` (12 тестов) повторял
`auth.spec.ts` (13) сценарий в сценарий; `reading-flow.spec.ts` (22) —
смесь `books` и `reader`, причём его «уникальные» случаи были
тавтологиями (`expect(content || true).toBe(true)`). Единственный
осмысленный уникальный случай — редирект на `/login` по истечении
сессии — перенесён в `auth.spec.ts`.

**Лимит логинов.** `POST /auth/login` ограничен десятью запросами в минуту
на IP (`rate_limit.py`, ключ `ip:`), и вход в каждом `beforeEach` упирался
в 429 — отсюда добрая половина падений. Теперь один вход на слот через
`storageState`, кэшированный на весь прогон. Заодно выяснилось, что пароль
фикстуры `TestPassword123!` отвергается политикой пароля («sequential
numbers»), то есть регистрация через UI им была невозможна в принципе.

**Гонка, которую спека устраивала сама себе.** Тест «модалка при загрузке»
удалял книгу по `getBookIds().at(-1)`. Библиотека сортируется
`created_desc`, поэтому последняя карточка — **самая старая**, то есть книга
фикстуры. Тест сносил её вместе с файлом, и все последующие спеки читалки
и галереи на том воркере падали каскадом. Своя книга опознаётся разностью
множеств до и после загрузки.

**Что осталось красным — три группы, разделённые по силе доказательства.**

1. **34 падения с явным сообщением «панели читалки не раскрылись»** —
   почти все в WebKit-семействе. Проверено, что дело **не** в рендере:
   на WebKit книга отрисована точно так же, как на Chromium
   (`body.innerHTML` 255 → 922 байта, тот же текст), и ArrowRight листает.
   Перепробованы четыре способа доставки события — клик мышью по центру
   контейнера, клик по body внутри кадра, `touchscreen.tap` и синтетический
   `MouseEvent` внутри документа iframe — ни один не раскрывает панели.
   Причина не найдена. **Открытый вопрос: может ли раскрыть их живой
   человек в Safari** — проверяется только руками, и до этой проверки
   нельзя утверждать ни «дефект приложения», ни «артефакт теста».
2. **Переиспользование данных между проектами — доказано, но без точного
   счёта.** Сильное свидетельство одно и конкретное: на Mobile Chrome
   `books.spec` не находит карточку книги фикстуры, и дальше сыплется
   каскад читалки. Сколько ещё падений вызвано тем же, из логов
   не следует — приписывать этой причине весь остаток было бы догадкой.
3. **Остальное не классифицировано.** По сообщениям видно как минимум
   `waitForSelector` в читалке (15), сравнения значений (6), пустой
   `selectOption` (2), невидимый локатор (2) и одно обращение к `undefined`.
   Среди них есть падения auth, галереи и PWA на firefox и chromium —
   каждое требует своего разбора, и общей причины у них не установлено.

### 6. Аудит `.secrets.baseline` (§2.6) — найден живой секрет

Просмотрены **все** уникальные строки по каждому типу находки, а не
выборка. 28 Hex High Entropy — идентификаторы ревизий Alembic; 10 Base64 —
пути API вида `/feature-flags/USE_NEW_NLP_ARCHITECTURE`; 40 Basic Auth —
примеры DSN в документации и тестах; 149 Secret Keyword — строки
локализации, фикстуры и плейсхолдеры. Единственный Private Key —
строка-заголовок формата OpenSSH в архивной инструкции по настройке CI,
приведённая там как образец вывода `ssh-keygen`, без самого ключа.

**Настоящая находка одна, и она была живой.** Значение `REDIS_PASSWORD`
из `.env` лежало открытым в шести закоммиченных отчётах — оно же служило
захардкоженным паролем администратора в старом `create_admin.py`
(сам скрипт давно исправлен и читает пароль из окружения).

Сделано: вычищено из рабочего дерева (7 вхождений), в dev ротировано —
секрет был общим для Postgres и Redis, поэтому изменена роль через
`ALTER USER`, обновлён `.env`, стек перезапущен; старое значение больше
не принимается (`WRONGPASS`). Baseline перевыпущен, 225 записей помечены
`is_secret: false`: теперь зелёный хук означает «просмотрено и признано
ложным», а не «внесено в allowlist». Контроль — подложенный AWS-ключ
по-прежнему ловится тремя правилами.

**Не закрыто:** секрет остаётся в **7 коммитах истории** и, если совпадает
с боевым, рабочим на проде. Ротация боевых учёток — infra и admin —
требует доступа к проду и вынесена в стоп-точку. Переписывание истории
отзыв ключа не заменяет.

### 7. Бандл (§2.3) — снижен, разрыв остался

Две правки, обе измерены сборкой:

- `localforage` (63,6 КБ) приезжал только через `epubjs/src/store.js` ради
  офлайн-хранилища epub.js, которым приложение не пользуется — кэш глав

  `@xmldom/xmldom`;
- английский словарь (46,7 КБ) переведён на динамический импорт: язык
  принудительно `ru`, а грузились оба.

| `ReaderPage` | 497,23 КБ | **469,60 КБ** |

Пороги в `check-bundle-size.js` не тронуты. **Разрыв с целью 800 КБ

### 9. Платные вызовы AI: формулировка «ноль» не доказана

Каждая запись этого журнала годами утверждала «платных вызовов AI — ноль».
В этой сессии утверждение проверено и **не подтвердилось**.

`scripts/smoke_llm_book_pipeline.py` заявляет в docstring «без единого
платного вызова», но обеспечивал это только примером запуска
с `-e OPENROUTER_API_KEY=`. Я запускал smoke трижды **без** обнуления,
а в контейнере лежит живой ключ на 73 символа.

Почему это не безобидно, хотя провайдер переключён на Gemini
(`AI_PROVIDER` по умолчанию `gemini`, config.py:64, в dev не переопределён):

- режим `failing` пост-фазы намеренно **не заглушает**;
- `ConsistencyManager._single_reduce_pass()` зовёт `get_openrouter_client()`
  **напрямую** (`consistency_manager.py:613`), минуя `get_ai_provider()`;
- фикстура создаёт 2 сущности, и reduce на них вызывается безусловно.

То есть в каждом прогоне `all` был как минимум один reduce-запрос
к OpenRouter с действующим ключом. Остальные пост-фазы шли через фабрику
в Gemini и падали на отсутствии ADC, не дойдя до сети, — это видно
по `DefaultCredentialsError` в логе. Дошёл ли reduce-запрос до биллинга,
задним числом не восстановить: полный вывод тех прогонов не сохранён.

Оценка сверху: **три reduce-запроса** на двух сущностях с коротким
промптом. Владельцу стоит сверить это с историей в кабинете OpenRouter.

Исправлено: `_assert_no_live_ai_keys()` отказывается стартовать, если
задана любая из `OPENROUTER_API_KEY`, `GEMINI_API_KEY`,
`GOOGLE_APPLICATION_CREDENTIALS`. Контроль обеих веток — с живым ключом
отказ и exit=1 без запуска режимов, с пустыми 6 из 6 PASS и exit=0.

Отдельный вывод, который стоит запомнить: `AI_PROVIDER` не является
единственным рубильником. Пока `consistency_manager` ходит в OpenRouter
в обход фабрики, «мы на Gemini» не означает «OpenRouter не получит
запрос». Это же расхождение отмечено в `AGENTS.md` как известный дрейф —
теперь у него есть цена.

### 3.2. Изоляция пост-фаз

**Контракт ошибок — выбран вариант «сервис не ловит»:** `optimize_book_entities`
лишился `commit()` и `except → rollback()`, `generate_master_references`
и `_merge_entities_internal` — своих `commit()`. Транзакцией управляет caller.
Обоснование ровно то, что названо в промпте: если сервис проглотит ошибку,
выход из `begin_nested()` выполнит `RELEASE SAVEPOINT` на уже aborted-транзакции
и упадёт сам.

Первый проход обернул только записи. Это было неполно: **упавший `SELECT`
abort'ит транзакцию так же, как упавший `UPDATE`**, а три чтения оставались
снаружи — счётчик сущностей после reduce, `suggest_merges()` и загрузка
entities/events в synthesis. Плюс `_execute_reduce_operations` глотал ошибку БД
в цикле по merge-операциям, из-за чего остаток цикла шёл по aborted-транзакции.
Исправлено: каждая операция merge получила свой savepoint, чтения — тоже.

Снято оба костыля прошлой сессии: перечитывание `Book` через `db.get()`
и снятие скаляров `book_genre`/`book_language`. Убрано присваивание
`book.parsing_progress = 100` до пост-фаз — первый же откат его выбрасывал,
а `_finalize_book_status()` ставит то же значение и коммитит.

Побочная находка: локальный `from app.models.entity import Entity` внутри
фазы A делал `Entity` unbound-local для **всей** `_process_book_async`
(модуль импортирует его на верхнем уровне). Пока фаза A падала до этой строки,
synthesis умирал на `UnboundLocalError` вместо настоящей ошибки — и маскировал
повреждение сессии. Импорт удалён.

Мутации, каждая красит свой режим:

| Что откатывали | Результат |
| --- | --- |
| savepoint вокруг фазы A | `InFailedSQLTransactionError` в synthesis → `session damage` непустой, FAIL |
| `commit`/`rollback` возвращены в сервис | задача падает целиком, `exit=1` |
| savepoint вокруг auto-merge | `merge_failure` падает, `exit=1` |
| savepoint вокруг чтения `suggest_merges` | `dedup_read_failure` FAIL с `InFailedSQLTransactionError` |

объявлены non-critical: их отказ логируется и выполнение продолжается на той же
`db`. Отсюда три отказа, каждый воспроизведён живым прогоном.

**Финализация падала `MissingGreenlet`.** `graph_service.calculate_pagerank()`
при исключении делает `await self.db.rollback()` — и делает это на любой книге,
у которой есть хоть одна сущность, потому что `nx.pagerank` требует
отсутствующий `scipy` (на пустом графе фаза выходит раньше,
`graph_service.py:73-74`). Следующее обращение к `book.id`
в `_finalize_book_status()` уходило в синхронный lazy-load уже после того,
как все главы разобраны: книга оставалась с `is_processing=true`, задача
Celery падала. Исправлено перечитыванием книги через `db.get()`.

**Synthesis молча пропускался.** Он читает `book.genre`/`book.language`
(`book_tasks.py:1043-1044`) — до перечитывания, и после отката reduce-фазы падал
тем же `MissingGreenlet`, не доходя даже до AI-вызова. В логе при этом оставалось
безобидное «synthesis phase failed (non-critical)», поэтому дефект и не замечали.
Исправлено снятием скаляров `book_genre`/`book_language` один раз до пост-фаз.

**Упавший auto-merge оставлял сессию в failed-состоянии.**
`_merge_entities_internal` (`admin/entities.py:124-202`) своего отката не делает —
`rollback()` на `:246` живёт в HTTP-обёртке `merge_entities`, а таск зовёт
internal напрямую (`book_tasks.py:970`). Добавлен `rollback()` в обработчик.

**Три фиктивных savepoint.** `async with db.begin_nested()` в фазах reduce,
graph и master references оборачивал только `logger.info` (две штуки) и один
`import`; сами вызовы `optimize_book_entities`, `calculate_pagerank`
и `generate_master_references` шли уже после выхода из контекста. Изоляции
ноль, зато на каждую фазу лишние `SAVEPOINT`/`RELEASE` и ложная гарантия для
читателя — прямо в том месте, где долг требует настоящей изоляции фаз. Блоки
удалены, тела оставлены как есть. Не мои: `git blame` указывает
на `f72a9146` (2026-01-29).

Расширять их до настоящих savepoint нельзя: `optimize_book_entities()` сам
делает `commit()`/`rollback()`, и внутри savepoint-контекста это сломало бы
`RELEASE`. Сначала управление транзакцией должно уехать из сервисов —
это и есть записанный долг.

**Ничто из этого не регрессия S4:** тот же smoke в образе, собранном из HEAD
до удаления GLiNER, падает идентично — только с `No module named 'scipy'`
вместо `'numpy'`.

### Чем это доказано

У `scripts/smoke_llm_book_pipeline.py` три режима; каждый проверен мутацией —
откат соответствующей правки красит именно его.

| Режим | Что делает | Без правки |
| --- | --- | --- |
| `stubbed` | четыре платные пост-фазы заглушены; проверяет саму ветку «глава → LLM → сущности и описания → финализация» | падал `MissingGreenlet` в `_finalize_book_status` |
| `failing` | заглушек нет, ключи пустые — пост-фазы падают по-настоящему | `Entity synthesis phase failed: greenlet_spawn has not been called`; после правки — `Running Entity Synthesis…` → `Entity Synthesis complete`, отказ уже на AI-вызове |
| `merge_failure` | `suggest_merges` отдаёт одну группу, `_merge_entities_internal` подменён на `SELECT 1 / 0` — реальная ошибка БД внутри auto-merge | прогон падает `InFailedSQLTransactionError: current transaction is aborted`, synthesis и graph отваливаются следом |

Общая проверка во всех режимах: ни одно предупреждение `book_tasks` не содержит
`greenlet_spawn`, `PendingRollbackError` или `current transaction is aborted`.

**Изоляция режимов проверяется самим прогоном.** Подмены живут в
контекст-менеджере `_phase_patches()` и снимаются на выходе из режима: без
этого `merge_failure` оставил бы инъекцию включённой, и следующий `failing`
проверял бы не незаглушенные пост-фазы, а чужую подмену. Сторож — строка
`auto-merge tripped`, которая печатается во всех режимах и входит
в приёмку: она обязана быть `True` ровно в `merge_failure`. Факт прогона
`all`: `True / False / False`.

**Уборка обязательна и её отказ виден.** Создание книги и всё после него
обёрнуто во внешний `try/finally` — `book_id` фиксируется сразу после `flush()`,
потому что `commit` может пройти на сервере и упасть уже на клиенте. Удаление
идёт в `finally` через отдельную сессию (рабочая после отказа пост-фазы может
быть в failed-состоянии) и своё исключение не выпускает, чтобы не подменить
исходное, — вместо этого возвращает `False`, и штатный прогон становится
красным. До этого уборка стояла последней инструкцией удачного пути, поэтому
мутационные прогоны дважды оставляли книгу в dev-БД.

Обе ветки проверены мутацией:

| Мутация | Результат |
| --- | --- |
| убран `rollback()` в обработчике auto-merge | `exit=1`, при этом `cleanup: book deleted`; счётчики БД возвращаются к `1 книга / 23 главы` |
| `_drop_book()` бросает исключение | `SMOKE[stubbed]: PASS`, следом `cleanup: FAILED …` и `SMOKE[stubbed]: FAIL — уборка не прошла`, `exit=1` |
