# Выкатка на прод: порядок действий

Составлено 2026-08-05 после аудита живого прода и переработки
`scripts/deploy-production.sh`. Заменяет устные договорённости.

## Ноль. Прочитать, если давно не выкатывали

Три факта об этой инсталляции, на которых уже обжигались:

1. **Прод и мониторинг — один compose-проект `app`.** У `fancai_flower`,
   `fancai_netdata`, `fancai_victoriametrics`, `fancai_dozzle`
   и `fancai_uptime_kuma` та же метка `com.docker.compose.project`, только
   другой файл. Значит `--remove-orphans` или `down` по прод-файлу снесут
   мониторинг заодно. Только адресные операции.
2. **Тома с префиксом проекта:** `app_postgres_data`, `app_redis_data`,
   `app_frontend_build`. Docker молча создаёт том с опечаткой в имени,
   поэтому неверная ссылка выглядит как успех, а не как ошибка.
3. **База и пользователь называются `fancai`**, не `fancai_prod`
   и не `fancai_user`.

## Первая выкатка после 2026-08-05 — только вручную

Обычный запуск `./scripts/deploy-production.sh` здесь **не годится**:
на сервере лежит старая версия скрипта, и она себя не обновляет. Bash
читает файл по мере исполнения, а уже определённые функции не меняются
от `git pull` в середине прогона.

Поэтому первый раз код доставляется руками, и только потом запускается
новый скрипт.

```bash
# 1. Опубликовать код (с рабочей машины).
#    На момент составления это 131 коммит: 94 владельца и 37 из сессии.
git push origin main

# 2. На сервере: убрать локальные правки.
#    Проверено 2026-08-05 — обе уже есть в репозитории:
#    Caddyfile (allowlist на 4 IP) и docker-compose.prod.yml (Yandex Postbox).
ssh fancai
cd /opt/fancai/app
git stash push -m "server-edits-before-deploy" Caddyfile docker-compose.prod.yml

# 3. Подтянуть код вручную — именно этот шаг обычно делает update_code.
git fetch origin main
git merge --ff-only origin/main

# 4. Убедиться, что скрипт новый: функции ниже обязаны найтись.
grep -c 'publish_frontend_artifact\|quiesce_writers\|update_code' \
    scripts/deploy-production.sh   # ожидается >= 3

# 5. Запустить.
PURGE_STALE_QUEUES=true ./scripts/deploy-production.sh
```

Начиная со следующего раза шаги 2–4 делает сам скрипт: `update_code`
подтягивает `origin/main`, отказывается работать при правках
отслеживаемых файлов и, если HEAD сдвинулся, **перезапускает себя**
через `exec`.

Перезапуск не перестраховка. `git merge` заменяет в том числе сам
`deploy-production.sh`, а bash читает скрипт по мере исполнения,
по байтовым смещениям. Проверено экспериментом: скрипт, переписавший
себя на ходу, **молча прекращает работу с кодом 0** — строки после
перезаписи не выполняются вовсе. Без `exec` выкатка выглядела бы
успешной, не сделав ничего.

## Что делает скрипт и в каком порядке

Порядок не косметический — он обеспечивает годность точки восстановления.

```
check_prerequisites, validate_environment, update_code
preserve_current_images     ← прежние образы под тегом rollback-<ts>
build_images                ← три образа; простоя ещё нет
─────────────────────────── trap rollback ERR
quiesce_writers             ← стоп backend/celery/beat; Postgres и Redis живут
create_backup               ← pg_dump -Fc + снимок Redis + архив SPA
purge_stale_queues          ← DEL light, при остановленном воркере
run_migrations
start_services              ← up -d, затем ЯВНАЯ публикация SPA в том
health_check, verify_frontend_artifact, verify_deployment
```

Почему именно так:

- **сборка до простоя** — три `--no-cache` образа идут минуты, держать
  сервис остановленным всё это время незачем;
- **дамп после остановки писателей** — иначе точка восстановления
  не соответствует состоянию, в котором исполнится миграция;
- **очистка очереди при остановленном воркере** — иначе он начнёт
  разгребать её раньше, чем она очищена;
- **публикация SPA явным копированием** — Docker наполняет именованный
  том только когда тот пуст, поэтому build-only job новую сборку
  в том не переносит. Без этого шага фронт на проде не обновляется
  (так и вышло: SPA там был датирован 29 марта).

## Если что-то пошло не так

**Скрипт откатывает только КОД.** Образы возвращаются из тегов
`rollback-<ts>`, SPA — из архива `frontend_build.tar.gz`. База
не трогается: автоматический restore при провале сборки откатил бы
пользовательские записи, сделанные уже после бэкапа.

Восстановление базы — отдельная осознанная операция:

```bash
./scripts/deploy-production.sh restore-db /backups/<timestamp>
```

Она сама остановит писателей, потребует ввести `RESTORE` и поднимет
сервисы после. Дамп в формате custom, поэтому `psql < файл` его
не прочитает — только `pg_restore`.

## Независимая копия

`pgbackup` делает ежедневный дамп в `/backups/daily/`. Имя вводит
в заблуждение: `fancai-latest.sql.gz` — это **custom-формат** (`PGDMP`),
а не gzip-архив SQL. Проверяется и восстанавливается через `pg_restore`:

```bash
docker exec fancai_pgbackup pg_restore --list /backups/daily/fancai-latest.sql.gz | head
```

## Проверка после выкатки

Скрипт проверяет сам: здоровье бэкенда изнутри контейнера, совпадение
опубликованного SPA с собранным образом, и что воркер слушает все три
очереди — `heavy`, `normal`, `light`. Последнее не формальность: очереди
задаются в `CMD` образа celery, и без его пересборки парсинг книг
остаётся без потребителя.

Руками остаётся то, что автоматика не покрывает:

- открыть книгу в читалке и проверить, что главы рендерятся;
- убедиться, что интерфейс обновился, а не отдаётся из кэша: SPA
  обслуживается service worker'ом, который не форсирует обновление.

Проверка «на проде именно новый код» делается не на глаз и не по совпадению
файлов, а поиском своей правки в опубликованном чанке. Пример с 2026-08-07:

```bash
# признак, добавленный сессией, обязан найтись в боевом бандле
curl -s https://fancai.ru/assets/js/ReaderPage-<hash>.js | grep -c reader-ready
```

Про Safari отдельно: e2e на `webkit` и `Mobile Safari` зелёные с 2026-08-07,
но клики и свайпы внутри книги там не работают и работать не могут —
ограничение движка, разбор в `progress.md`. Панели раскрываются `Escape`.

## Две грабли, на которых уже стояли

1. **`git push` до выкатки обязателен.** `update_code` делает
   `git fetch` + `merge --ff-only origin/main`, то есть выкатывает то, что
   в `origin`, а не то, что у вас локально. 2026-08-07 семь коммитов лежали
   только локально: без push скрипт отработал бы успешно и опубликовал
   предыдущий коммит. Сверять до старта:
   `[ "$(git rev-parse origin/main)" = "$(git rev-parse HEAD)" ]`.
2. **SSH обрывается примерно на 60-й секунде** — 2026-08-06 на 61-й,
   2026-08-07 на 64-й и ещё раз на 61-й. `tmux` на сервере НЕТ, поэтому
   длинные шаги только так:
   `setsid nohup <команда> > /tmp/<лог> 2>&1 < /dev/null &`, дальше опрос лога.

## Правка `Caddyfile`: два условия

1. **Нужен `--force-recreate`, а не `reload`.** `Caddyfile` смонтирован
   одиночным файлом, после `git merge` у него новый inode, и работающий
   контейнер продолжает держать старый. Проверено вживую 2026-08-07: на хосте
   новый адрес есть, `docker exec fancai_caddy grep` его не находит.
2. **Не иметь `MONITOR_PASSWORD_HASH` в оболочке.** В `.env` он записан
   с удвоённым `$` (`$$2a$14$…`) — так требует интерполяция compose.
   `set -a; . ./.env` заставляет оболочку развернуть `$$` в PID, и этот мусор
   перебивает значение из `.env`: Caddy падает с
   `base64-decoding password: illegal base64 data`, уходит в restart-цикл,
   сайт лежит. Именно так был получен простой 2026-08-07. Проверка:
   `docker exec fancai_caddy printenv MONITOR_PASSWORD_HASH | wc -c` — должно
   быть 60, а не 63.
